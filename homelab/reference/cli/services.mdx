## techstack api services run-action

Run a governed StackKits service action.

Derives stack, server, agent, kit and service authority from fresh canonical inventory. Every agent-executed mutation (`start`, `stop`, `restart`, `update`, `backup`, adopted applications included) runs as one governed RIL action card, its only write path: the card is derived from the service, its server and worker (an adopted application by its exact container, `update` with the pinned release, `backup` with the stack's backup contract), its one Gateway Decision is answered by the acting agent's equipment (no per-call approval flag), and the executor-bound primitive (`start-service`, `stop-service`, `restart-service`, `update-service` or `run-backup`) runs through the same lease, one-use claim, node proof, dispatcher and evidence as `/v1/ril/action-cards`. The response names the card in `action_card_id` and its execution in `job_id`; read it back with `get_action_card` for its status and evidence. `freeze` and `unfreeze` set the owner guardrail in the control plane without reaching the node. This operation only changes a service: a log page is requested with `POST /api/v1/registry/services/&#123;serviceId&#125;/logs` and read with `GET` on the same path. Exact replays converge on the same card receipt and a different body under the same key is 409; the raw Idempotency-Key is never persisted. A start or restart is followed by StackKits verify before measured state changes. Agent-executed actions refuse with 409 `maintenance_active` while the server is being rebooted or updated, a kit whose backups are managed refuses `backup` with 403 `managed_backup_custody`, and a locked service, application group or (for `update`) stack refuses on both entries.

```bash
techstack api services run-action <service-id> [flags]
```

## techstack api services start-own-application-operation

Queues one StackKits own-application step for an application StackKits runs as an own application and Stack it adopted: status or logs (reads), backup (Owner approved, a node snapshot holding every own application volume), or the dry run of a mutation: review (start, stop, restart or rollback), update_review (a newer version tag of its own image, optionally allow_major), checkpoint_rollback_review or checkpoint_discard_review (the data checkpoint of a tag update).
