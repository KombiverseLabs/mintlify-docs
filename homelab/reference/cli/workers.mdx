## techstack api workers identity upgrade approve

Approve the key a legacy server proposed.

Binds the pending key named by `key_thumbprint`, which makes the worker key-bound (bearer-only requests are denied afterwards). Requires the owner and a fresh multi-factor sign-in (at most 300 seconds old). The approving subject and time are recorded with the identity and logged. 409 `identity_upgrade_not_pending` when no unexpired pending key has that fingerprint.

```bash
techstack api workers identity upgrade approve <id> [flags]
```

<Warning>Requires confirmation: This operation decides which key may command the server; approve only a key whose fingerprint the Guard logs on the server. Pass `--yes` or answer the prompt; a non-interactive run without `--yes` stops before any request with exit code 9.</Warning>

## techstack api workers outcomes resolve

Release an unresolved kombify Guard operation outcome.

Commits an append-only operator resolution revision for an operation whose outcome is unknown and releases the worker's fence. `disposition` is `verified_applied` (the effect is in place), `verified_not_applied` (nothing happened) or `accept_unknown` (release without a verified outcome); `note` records what was verified. The actor is the authenticated subject and is recorded with the revision; a Guard cannot commit these dispositions. The person's own session needs a fresh multi-factor sign-in (at most 300 seconds old); an agent acting for the person needs none. `expected_revision` must be the revision the list returned, otherwise 409 `outcome_revision_stale`. The body is decoded strictly: exact keys, no unknown fields.

```bash
techstack api workers outcomes resolve <id> <command-id> [flags]
```

<Warning>Requires confirmation: This operation releases the fence of an operation whose outcome was never settled, so conflicting changes may run against the server. Pass `--yes` or answer the prompt; a non-interactive run without `--yes` stops before any request with exit code 9.</Warning>

## techstack api workers tenant-handoff confirm

Confirm the handoff of a retired server's command evidence.

The owner, as custodian of a detached or retired server, confirms that the command evidence its Guard still holds (journal entries, outcomes and identity state) may leave the server by `export` (an archive the operator takes off the server) or `quarantine` (a root-only directory outside the Guard state). The response shows a one-time `confirmation` exactly once and is valid for 72 hours. It is bound to the host key the worker used. The operator passes it to `techstack agent handoff `--server` --confirmation-file`, which has the control plane verify it for this server's key, then moves and securely removes the evidence and records a receipt. Pairing a server whose host key served another tenant, or that declares another tenant's evidence, is refused (409 `tenant_handoff_required`) until a receipt of that tenant is consumed. A receipt is consumed once, by the pairing that proves the confirmed key, before expiry; only that pairing may repeat it within 15 minutes (409 `tenant_handoff_invalid` otherwise). Requires the owner and a fresh multi-factor sign-in (at most 300 seconds old). 409 `tenant_handoff_worker_active` while the worker is not revoked or rejected, 409 `tenant_handoff_unbindable` for a worker that never bound a host key. A worker of another tenant or owner is 404.

```bash
techstack api workers tenant-handoff confirm <id> [flags]
```

## techstack api workers updates show

Read a server's update setting and pending StackKits release.

For the owner of the worker. `behavior` is the server's one update setting for its StackKits release and the applications it manages (D-2026-11-12-06): `ask` (default; checked application versions are offered with one click), `automatic` (StackKits releases start without a click; checked application versions apply in the maintenance window once that action exists) or `with_stackkits_releases` (applications change only with a StackKits release). Security fixes are offered in every setting. The per-application facts are on the service `version`.
