## techstack api stacks create

Create a StackKit deployment in the owner's Homelab.

Creates an internal StackKit deployment under the authenticated B2C
owner's singleton Homelab from the canonical StackKits stack-spec
payload supplied as `stack_spec`. The legacy `/stacks` route and
`stack_id` response field identify that deployment; they do not create
or select a second Homelab product. One TechStack instance can serve
many owners, each with their own Homelab. Legacy
`user_config`/kombination payloads remain accepted at this compatibility
boundary. Wizard clients should send a stable `X-Idempotency-Key`;
retries with the same key and payload return the original deployment,
planned server, and provisioning job.

```bash
techstack api stacks create [flags]
```

<Warning>Requires confirmation: This operation creates the StackKit deployment and starts provisioning, which can order billed servers. Pass `--yes` or answer the prompt; a non-interactive run without `--yes` stops before any request with exit code 9.</Warning>

## techstack api stacks managed-runtimes add

Add one managed Node through native provider control.

Creates or resumes one deterministic Add-Server job for the exact
owned StackKit deployment. The standard `Idempotency-Key` is mandatory.
Replaying the same key with the same canonical request returns the original
job, lease, runtime-server, resource-generation, and provider-operation
correlations; reusing it with different intent fails with 409.

The raw key is never persisted or returned. A lost response or an
uncertain native-admission outcome remains resumable only with the
same key. HTTP acceptance means native admission is durable and
provider reconciliation is pending; it never claims that the VM is
already provisioned or healthy. Fresh admission atomically reserves
the authenticated tenant/owner capacity slot with the lease generation
and provider operation. When authoritative native admission finds that
bounded capacity full, it persists a non-retryable 403 outcome and
replaying that denied job returns the same outcome. Exact replays of an
already committed admission reuse its existing reservation. This version
has no automatic reservation release: terminal or local decommission
state alone does not free a slot. Lease inventory and feature-delivery
flags never authorize or deny capacity.
Hosted fresh admission also requires the v2-signed commercial runtime
and provider entitlements plus the signed `cloud.runtime.credits`
`managed_servers` mode/limit decision; feature flags alone never grant
provider capacity. Self-host OSS uses its construction-fixed static
release-manifest policy instead of a SaaS entitlement dependency.

```bash
techstack api stacks managed-runtimes add <stack-id> [flags]
```

<Warning>Requires confirmation: This operation orders an additional managed server for the StackKit deployment and is billed. Pass `--yes` or answer the prompt; a non-interactive run without `--yes` stops before any request with exit code 9.</Warning>

| HTTP | `POST /api/v1/stacks/{id}/managed-runtimes` |
| Changes state | Yes |
| MCP tool | `add_managed_runtime_server` |

| --- | --- | --- |
| `<stack-id>` | string | **Required.** Stack ID. |
| `--ionos-datacenter` | string | IONOS datacenter alias for provider_region; ignored for other canonical providers. |
| `--node-role` | string | One of `foundation`, `worker`, `storage`. Default `"worker"`. |
| `--provider-id` | string | **Required.** Canonical executable provider identifier; historical display aliases are rejected. One of `centron`, `ionos`. |

## techstack api stacks resume-enrollment

Resume one overdue managed Node wait on its exact existing VM.

Authenticated, idempotent recovery for a persisted `waiting_enrollment`,
`waiting_provider_provision`, or `waiting_canonical_guard` job whose
`next_resume_at` has been overdue beyond the bounded grace period. The
server validates the owned StackKit deployment, source job, wait reason,
exact lease, active foundation role, and canonical Node as one operation. It
atomically retires the exact source wait, creates or rehydrates one
deterministic replacement deploy bound to the same lease and Node,
and replays that job on later calls. Before handler entry,
queue workers atomically acquire the durable `tenant/stack` compatibility
execution claim; this serializes different jobs for the same StackKit
deployment across Techstack
replicas. The claim remains durable `running` until the handler exits,
including during cancellation. This endpoint never invokes provider VM
creation or selects a newer VM. A replacement found durable `running`
after a crash remains fail-closed, is reported as the same job, and is
never duplicated automatically; runtime-action reconciliation remains a
separate operator concern.

```bash
techstack api stacks resume-enrollment <stack-id> [flags]
```

| | |
| --- | --- |
| HTTP | `POST /api/v1/stacks/{id}/resume-enrollment` |
| Changes state | Yes |
| MCP tool | `resume_stack_enrollment` |

| Argument | Type | Description |
| --- | --- | --- |
| `<stack-id>` | string | **Required.** Stack ID. |
| `--job-id` | string | **Required.** Persisted source job currently projected as waiting_enrollment. |
| `--lease-id` | string | **Required.** Exact managed foundation lease already bound to the source job. |
| `--body` | json | JSON request body (`application/json`) as a literal, `@path` or `-` for stdin. |

## techstack api stacks routing ensure

Ensure the desired routing overlay for one exact StackKit deployment and Node.

Atomically persists an idempotent, revisioned routing overlay without mutating the user's immutable intent. server_id is always exact and mandatory. lease_id is mandatory for managed runtimes and omitted for a local/Basement runtime which has no lease. For a managed target, a true ensure_rollout request dispatches the existing deploy pipeline only after proving that its selected active foundation lease and canonical Node equal this exact target. The API never reports the resulting job as already applied. The overlay is consumed only while deriving StackKits artifacts and this path never creates or selects a replacement VM.
