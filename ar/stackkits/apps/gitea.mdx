يوفر Gitea حالة الاستخدام [التطوير](/ar/guides/stackkits/use-cases/development). يشغّل حمل عمل التطوير مع Gitea خادم Git خاصًا في حاوية بدون صلاحيات الجذر (rootless) مع SQLite على عقدة واحدة مختارة. التسجيل العام معطّل وتُفرض الخصوصية على المستودعات الجديدة. لا يكشف SSH، ولا يثبّت منفّذ CI، ولا يفعّل Actions؛ وتبقى سير العمل للمستخدمين الإضافيين ورموز API عمليات أصلية في Gitea. يسرد [كتالوج حالات الاستخدام](/ar/stackkits/reference/use-case-catalog) المكونات التي يعلنها الإصدار المنشور.

## ما هو

Gitea هو مكان خاص لحفظ شيفرتك، يشبه نسخة صغيرة ذاتية التشغيل من موقع استضافة الشيفرة. تدفع مشاريعك إليه بأدوات Git المعتادة وتبقيها خاصة. يتضمنه StackKit كي لا تضطر مستودعاتك إلى العيش عند مزوّد خارجي.

## الأطقم وحالات الاستخدام التي تتضمنه

Gitea هو التطبيق الافتراضي لجزء Developer Platform في حالة الاستخدام Dev. يستخدم المثال أدناه `basement-kit` على Compose المستقل. وفقًا لحالة الأدلة في صفحة [التطوير](/ar/guides/stackkits/use-cases/development)، فهو قابل للاختيار لكنه لم يُتحقق منه بعد على مستوى دورة الحياة.

## كيف تفتحه

افتح المسار الذي تضبطه لحمل العمل؛ يستخدم المثال `https://dev.home.test`. يجب أن يُحَل اسم المضيف إلى مضيفك من كل عميل، كما هو موضح أدناه.

## اختر حمل عمل التطوير صراحةً

من مساحة عمل مالك فارغة، اختر Gitea وأنشئ حفظ المالك المحلي له:

```bash
stackkit init basement-kit --platform standalone-compose \
  --use-case dev --use-case-alternative dev=gitea \
  --use-case-alternative basement-core=standalone \
  --module-compute-profile stackkits-basement-core-runtime=standard \
  --module-compute-profile stackkits-gitea-runtime=standard \
  --owner-source local --owner-email owner@example.com --non-interactive
```

قبل التوليد، ادمج الحقول التالية في الأقسام الموجودة `capabilities` و`data` و`routes` من [StackSpec](/ar/guides/stackkits/configure-stack-spec) الخاص بك. حافظ على بقية مدخلاتها. يستخدم هذا المقتطع الموقع الأولي `home` وسياسة الوصول `home-private`؛ كيّف تلك المراجع ونطاق المنزل وجذور التخزين على المضيف بما يناسب مضيفك الفعلي.

```yaml
capabilities:
  enable: [internal-pki]
data:
  bindings:
    dev:
      classes: [personal]
      primarySiteRef: home
routes:
  dev:
    serviceRef: dev
    moduleRef: stackkits-gitea-runtime
    exposure: local
    protocol: https
    port: 443
    targetPort: 3000
    host: dev.home.test
    path: /
    accessPolicyRef: home-private
```

يتطلب Gitea مسار HTTPS الصريح هذا وربط البيانات للحصول على روابط استنساخ أصلية قابلة للاستخدام. تحقق من النتيجة ثم ولّدها:

```bash
stackkit validate
stackkit generate --local-node main --local-site home
```

ثم اتبع دورة التسليم المعتادة: تحقق، وافحص الخطة، ثم طبّق وتحقق كما هو موثق في [المراجعة والتطبيق والتحقق](/ar/guides/stackkits/review-plan-and-apply). يجب أن يفي جرد المضيف المرصود بملفات الوحدات المختارة؛ والإعداد المثالي ليس دليلًا على العتاد.

## وفّر الاسم وثق بأن المسار يعمل

يحتاج Git عبر HTTPS الأصلي إلى أمرين يجب أن يستوفيهما مضيفك مسبقًا:

- يجب أن يُحَل اسم مضيف المسار (يستخدم المثال `dev.home.test`) إلى ذلك المضيف من كل عميل تنوي الاستنساخ منه.
- يجب أن تثق عملاء Git بشهادة المرجع المصدِّق الداخلي للمضيف. وبدون ثقة العميل، يفشل الاستنساخ عبر HTTPS قبل المصادقة.

## اكشف كلمة مرور المالك وسجّل الدخول

يرحّل أول تشغيل قاعدة بيانات SQLite وينشئ المسؤول `owner` قبل خدمة الطلبات؛ ويأتي بريد المالك من هوية المالك المحلية، ويُحفظ المرجع `owner-password` في حفظ الأسرار المحلي القائم. اقرأ كلمة المرور في طرفية خاصة:

```bash
stackkit secrets reveal --workload dev --slot owner-password
```

يقبل الأمر فقط الفتحات (slots) المعلنة في StackSpec الحالي الذي جرى التحقق منه، ويكتب القيمة إلى stdout — وليس إلى سجلات النشر أبدًا — ولا ينشئ كلمة مرور ولا يعيد تعيينها. أما وجود مسؤول غير مطابق أو قاعدة بيانات مستخدمين غير مملوكة فيُفشل التسليم دون استبدال الحسابات أو إعادة تعيين كلمات المرور.

## الاستخدام الأول

1. اكشف كلمة مرور المالك بالأمر أعلاه في طرفية خاصة.
2. افتح مسار Gitea وسجّل الدخول باسم `owner`.
3. أنشئ مستودعًا خاصًا.
4. انسخ رابط استنساخه عبر HTTPS واستنسخه من عميل حقيقي باستخدام تخزين بيانات اعتماد Git الأصلي لديك.
5. ادفع إيداعًا تجريبيًا صغيرًا.

سجّل الدخول باسم `owner`، وأنشئ مستودعًا خاصًا، واستخدم رابط استنساخه عبر HTTPS مع تخزين بيانات اعتماد Git الأصلي لديك. يصادق Git مباشرةً مع Gitea: لا توجد بوابة مصادقة أمامية في المتصفح تعترض طلبات Git. إن جاهزية تبلّغ فقط عن إمكانية الوصول إلى عملية HTTP وSQLite لا تثبت أنك استنسخت أو دفعت أو استرددت أي شيء — اختبر دفعًا فعليًا من عميل مقصود.

## حدود التخزين والاسترداد

| التخصيص | مسار الحاوية | المحتويات |
| --- | --- | --- |
| `gitea/data` | `/var/lib/gitea` | قاعدة بيانات SQLite والمستودعات وكائنات LFS وبيانات التطبيق |
| `gitea/config` | `/etc/gitea` | `app.ini` ومفاتيح/إعدادات التطبيق المحفوظة |

ينتمي كلا المجلدين المسمّيين إلى عقد البيانات والنسخ الاحتياطي لحمل العمل. يقوم الاسترداد الصحيح بإيقاف الكاتب الوحيد للتطبيق مؤقتًا، ويلتقط المجلدين معًا، ويفعّلهما معًا مع إيقاف الكتابة — ونسخ ملف SQLite حيًا وحده لا يفي بهذا العقد. اتبع [النسخ الاحتياطي والاستعادة](/ar/guides/stackkits/back-up-and-restore) لدورة حياة مساحة العمل. يستخدم Gitea بدون صلاحيات الجذر وبصلاحيات الجذر تخطيطات مختلفة، لذا فإن تبديل الصورة ليس ترحيلًا للتخزين.

## ما المتوقع

Gitea هو خادم صغير واحد يستخدم SQLite على عقدة واحدة مختارة. صفحات تسجيل الدخول والمستودعات سريعة لأسرة. إذا تحمّلت الصفحة لكن الاستنساخ فشل، فالسبب المعتاد هو حل الأسماء أو الثقة بالشهادة، وليس Gitea نفسه.

## إذا حدث خطأ

- يفشل الاستنساخ قبل طلب كلمة المرور: اسم المضيف لا يُحَل من ذلك العميل، أو أن العميل لا يثق بشهادة المرجع المصدِّق الداخلي.
- لا تتذكر كلمة مرور المالك: اكشفها مجددًا بـ `stackkit secrets reveal --workload dev --slot owner-password`؛ فالأمر لا ينشئ كلمة مرور ولا يعيد تعيينها.
- يفشل التسليم بسبب مسؤول أو قاعدة بيانات مستخدمين موجودة: لا يستبدل الحسابات ولا يعيد تعيين كلمات المرور؛ عالج التعارض عمدًا أولًا.
- قارن أي عنوان بمخرجات النشر وراجع [استكشاف الأخطاء وإصلاحها](/ar/guides/stackkits/troubleshooting).

## الحدود المعروفة

- SSH غير مكشوف؛ وHTTPS الأصلي هو مسار وصول Git الموثق.
- لا تُثبَّت Gitea Actions ولا منفّذو CI؛ ولا يوجد حتى الآن مسار موثق لدمج المنفّذ.
- إعادة إنشاء الحاوية بالقوة تُبقي وصول المالك وبيانات المستودعات الخاصة الوصفية وإعدادات التطبيق، لكن التوفير الكامل لمضيف Linux وتوزيع DNS/CA الحقيقي على الشبكة المحلية ودورة نسخ احتياطي/استعادة كاملة هي مستويات أدلة منفصلة وغير مثبتة هنا.
