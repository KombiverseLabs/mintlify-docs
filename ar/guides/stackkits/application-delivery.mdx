يفصل StackKits بين اختيار التطبيق وتسليمه. يختار الـ workload مثل Files بديله من التطبيقات، بينما يحدد `runtimeAdapterRef` كيف يُسلَّم ذلك الـ workload الواحد.

افحص المصفوفة المضمّنة في إصدارك المثبّت:

```bash
stackkit app compatibility --json
```

## اختيار المحوّل

| المحوّل | الحالة الحالية | استخدمه عندما |
| --- | --- | --- |
| `standalone-compose` | مدعوم | تحتاج إلى مسار الـ workload المحلي مع قدرة نسخ احتياطي واستعادة معلنة ودون منصة تطبيقات منفصلة. |
| [Coolify](/ar/stackkits/apps/coolify) | مدعوم | تشغّل بالفعل منصة التطبيقات المولّدة وتقبل أن النسخ الاحتياطي والاستعادة للـ workload خارج نطاق هذا المحوّل. |
| [Komodo](/ar/stackkits/apps/komodo) | تجريبي (Beta) | تقبل عن قصد نضج المحوّل التجريبي وتتحقق منه في مساحة عملك. |

يصف النضج عقد الكتالوج، لا الصحة الملاحَظة على مضيفك. تسرد مصفوفة [توافق تسليم التطبيقات](/ar/stackkits/reference/application-delivery-compatibility) المولّدة قدرات النشر والمسار وTLS والنسخ الاحتياطي والاستعادة لكل workload ومحوّل في الإصدار المنشور. افحص الصف الخاص بتطبيقك المختار؛ فدعم المنصة للنشر وحده لا يثبت قدرتها على الاسترداد. لا تفترض دعماً عاماً لمكوّن لا تسرده المصفوفة.

لـ Basement Kit مستقل، ابدأ بـ `standalone-compose` ما لم تكن تشغّل عن قصد إحدى منصات التطبيقات:

```json
{
  "workloads": {
    "files": {
      "alternative": "cloudreve",
      "runtimeAdapterRef": "standalone-compose",
      "placement": {
        "siteRefs": ["home"],
        "nodeRefs": ["main"]
      }
    }
  }
}
```

## مالك واحد لكل workload

- لا تمرّر الـ workload نفسه عبر Coolify وCompose المستقل في الوقت نفسه.
- لا تضف وسوم Docker أو مسارات مولّدة يدوياً.
- تعامل مع Komodo كخيار تجريبي في هذا الإصدار، لا كبديل افتراضي.
- تحقق من النية المتغيرة وافحص الخطة المحلولة قبل تطبيق محوّل مختلف.

راجع [خدمات المنصة](/ar/stackkits/apps/overview) لتكاملات المنصة، و[إعداد StackSpec](/ar/guides/stackkits/configure-stack-spec) لسير التحرير الكامل.
