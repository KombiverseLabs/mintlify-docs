يفصل StackKits بين اختيار التطبيقات ومسؤولية التنفيذ. Standalone Compose هو الخيار الأصلي الافتراضي. Komodo منصة عمليات بلا متجر تطبيقات. Marketplace حالة استخدام اختيارية مخططة تعتمد على Coolify؛ وCoolify تطبيق ضمنها، وليس هدف تشغيل أصلياً.

افحص المصفوفة المضمّنة في إصدارك المثبّت:

```bash
stackkit app compatibility --json
```

## اختيار المحوّل

| المحوّل | الحالة الحالية | استخدمه عندما |
| --- | --- | --- |
| `standalone-compose` | الخيار الأصلي الافتراضي | استخدم مسار workload المعلن في الإصدار المثبت وافحص دليل دورة حياته. |
| [Coolify](/ar/stackkits/apps/coolify) | تطبيق Marketplace مخطط | لا يُثبّت بوصفه Marketplace إلا بعد إدراجه في الكتالوج المنشور والتحقق من دورة حياته. |
| [Komodo](/ar/stackkits/apps/komodo) | مسودة منصة عمليات | اختره صراحةً ضمن نطاق workloads الذي يثبته دليل النسخة المثبتة الحالية فقط. |

تصف مصفوفة [توافق تسليم التطبيقات](/ar/stackkits/reference/application-delivery-compatibility) المنشورة عقود المحوّلات المعلنة. لا تثبت الصفوف التاريخية الدعم للنسخة المثبتة الحالية. افحص دليل دورة حياة التطبيق والإصدار؛ فالنشر وحده لا يثبت النسخ الاحتياطي أو الاستعادة.

لـ Basement Kit مستقل، ابدأ بـ `standalone-compose` ما لم تكن تشغّل عن قصد إحدى منصات التطبيقات:

```json
{
  "workloads": {
    "files": {
      "alternative": "cloudreve",
      "runtimeAdapterRef": "standalone-compose",
      "placement": {
        "siteRefs": ["home"],
        "nodeRefs": ["main"]
      }
    }
  }
}
```

## مالك واحد لكل workload

- لا تمرّر الـ workload نفسه عبر Coolify وCompose المستقل في الوقت نفسه.
- لا تضف وسوم Docker أو مسارات مولّدة يدوياً.
- يحتاج مسار Komodo الصريح إلى دليل للنسخة المثبتة الحالية؛ وليس الخيار الافتراضي أو متجر تطبيقات.
- تحقق من النية المتغيرة وافحص الخطة المحلولة قبل تطبيق محوّل مختلف.

راجع [خدمات المنصة](/ar/stackkits/apps/overview) لتكاملات المنصة، و[إعداد StackSpec](/ar/guides/stackkits/configure-stack-spec) لسير التحرير الكامل.
