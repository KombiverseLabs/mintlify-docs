استخدم مساحة العمل نفسها وCLI المُصدَر نفسه من الإعداد حتى التحقق. الملفات المولّدة مخرجات تحمل الأدلة؛ ويبقى StackSpec هو المدخل القابل للتحرير.

## 1. تحقق وولّد

```bash
stackkit validate
stackkit generate
```

يكتب التوليد الخطة المحلولة وبيان التوليد والإيصال والمخرجات المحكومة تحت جذر المخرجات المضبوط.

## 2. افحص الخطة

```bash
stackkit plan --json
```

قبل التطبيق، تأكد من:

- وجود تجزئتي الخطة والمواصفة
- أن `readiness.generation.status` هو `ready`
- أن `readiness.apply.status` هو `ready`
- أن الـ workloads والمواقع والعقد والمحوّل المختارة تطابق نيتك
- أن لكل مخرَج مولّد مالكاً ومساراً متوقعاً

يفحص `plan` الإغلاق الأصلي v2 دون استدعاء منفّذ. الخطة الجاهزة شرط لازم، لكنها ليست دليلاً على أن المضيف قد تغيّر بالفعل.

## 3. طبّق صراحةً

```bash
stackkit apply
```

راجع مطالبة الموافقة المحلية. `apply` هي الخطوة التي تغيّر المضيف. يترك مثبّت أدوات التشغيل هذه الخطوة لك؛ أما تمهيد Basement في `base.stackkit.cc` فينفّذ التطبيق الأولي بالفعل. بعد ذلك التمهيد، طبّق مجدداً فقط لتغيير مقصود في الإعداد.

## 4. تحقق من النتيجة

```bash
stackkit verify --http --json
stackkit drift detect --json
stackkit logs list --json
```

احتفظ بناتج JSON مع مساحة العمل. فهو يربط النتيجة الملاحَظة بدورة الحياة المحلية بدلاً من لقطة شاشة أو ملف Compose معدَّل.

<Warning>
  توقف عندما تبلّغ الخطة المحلولة عن عائق في التطبيق. لا تتجاوزه بتعديلات مباشرة على Docker أو Compose أو الملفات المولّدة؛ صحّح StackSpec أو المضيف الهدف وولّد من جديد.
</Warning>
