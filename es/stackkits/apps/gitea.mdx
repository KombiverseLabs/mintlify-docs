Gitea proporciona el caso de uso [Desarrollo](/es/guides/stackkits/use-cases/development). La carga de trabajo de desarrollo con Gitea ejecuta un servidor Git privado en un contenedor sin privilegios de root con SQLite en un nodo seleccionado. El registro público está desactivado y los repositorios nuevos se fuerzan a privados. No expone SSH, no instala un runner de CI ni activa Actions; los flujos de trabajo para usuarios adicionales y tokens de API siguen siendo operaciones nativas de Gitea. El [catálogo de casos de uso](/es/stackkits/reference/use-case-catalog) enumera los componentes que declara la versión publicada.

## Qué es

Gitea es un lugar privado para guardar tu código, similar a una pequeña versión autoalojada de un sitio web de alojamiento de código. Subes proyectos con las herramientas Git habituales y los mantienes privados. Un StackKit lo incluye para que tus repositorios no tengan que vivir con un proveedor externo.

## Qué kits y casos de uso lo incluyen

Gitea es la aplicación por defecto de la parte Developer Platform del caso de uso Dev. El ejemplo siguiente usa `basement-kit` en Compose independiente. Según el estado de la evidencia de la página [Desarrollo](/es/guides/stackkits/use-cases/development), es seleccionable pero todavía no está verificado en el ciclo de vida.

## Cómo abrirlo

Abre la ruta que configures para la carga de trabajo; el ejemplo usa `https://dev.home.test`. El nombre de host debe resolverse a tu host desde todos los clientes, como se describe más abajo.

## Seleccionar explícitamente la carga de trabajo de desarrollo

Desde un espacio de trabajo de propietario vacío, selecciona Gitea y establece su custodia local del propietario:

```bash
stackkit init basement-kit --platform standalone-compose \
  --use-case dev --use-case-alternative dev=gitea \
  --use-case-alternative basement-core=standalone \
  --module-compute-profile stackkits-basement-core-runtime=standard \
  --module-compute-profile stackkits-gitea-runtime=standard \
  --owner-source local --owner-email owner@example.com --non-interactive
```

Antes de generar, combina los siguientes campos con las secciones existentes `capabilities`, `data` y `routes` de tu [StackSpec](/es/guides/stackkits/configure-stack-spec). Conserva sus demás entradas. Este fragmento usa el sitio inicial `home` y la política de acceso `home-private`; adapta esas referencias, el dominio doméstico y las raíces de almacenamiento del host a tu host real.

```yaml
capabilities:
  enable: [internal-pki]
data:
  bindings:
    dev:
      classes: [personal]
      primarySiteRef: home
routes:
  dev:
    serviceRef: dev
    moduleRef: stackkits-gitea-runtime
    exposure: local
    protocol: https
    port: 443
    targetPort: 3000
    host: dev.home.test
    path: /
    accessPolicyRef: home-private
```

Gitea necesita esta ruta HTTPS explícita y esta vinculación de datos para obtener URL de clonación nativas utilizables. Valida y genera el resultado:

```bash
stackkit validate
stackkit generate --local-node main --local-site home
```

Después sigue el ciclo de vida de entrega normal: validar, inspeccionar el plan, y aplicar y verificar como se documenta en [Revisar, aplicar y verificar](/es/guides/stackkits/review-plan-and-apply). El inventario observado del host debe satisfacer los perfiles de módulo seleccionados; la configuración de ejemplo no es evidencia de hardware.

## Proporcionar el nombre y confiar en que la ruta funciona

El Git HTTPS nativo necesita dos cosas que tu host ya debe cumplir:

- El nombre de host de la ruta (el ejemplo usa `dev.home.test`) debe resolverse a ese host desde todos los clientes desde los que quieras clonar.
- Los clientes Git deben confiar en el certificado de la CA interna del host. Sin confianza del cliente, la clonación HTTPS falla antes de la autenticación.

## Revelar la contraseña del propietario e iniciar sesión

El primer arranque migra la base de datos SQLite y crea el administrador `owner` antes de atender tráfico; el correo del propietario procede de tu identidad local de propietario, y la referencia `owner-password` se guarda en la custodia local de secretos existente. Lee la contraseña en un terminal privado:

```bash
stackkit secrets reveal --workload dev --slot owner-password
```

El comando solo acepta las ranuras declaradas por la StackSpec validada actual, escribe el valor en stdout (nunca en los registros del despliegue) y no crea ni restablece ninguna contraseña. Un administrador existente que no coincida o una base de datos de usuarios sin propietario hace fallar la entrega sin reemplazar cuentas ni restablecer contraseñas.

## Primer uso

1. Revela la contraseña del propietario con el comando anterior en un terminal privado.
2. Abre la ruta de Gitea e inicia sesión como `owner`.
3. Crea un repositorio privado.
4. Copia su URL de clonación HTTPS y clónalo desde un cliente real, usando el almacenamiento de credenciales nativo de Git.
5. Sube un pequeño commit de prueba.

Inicia sesión como `owner`, crea un repositorio privado y usa su URL de clonación HTTPS con el almacenamiento de credenciales nativo de Git. Git se autentica directamente con Gitea: ninguna puerta de forward-auth del navegador intercepta las peticiones de Git. Una comprobación de disponibilidad que solo informa de que el proceso HTTP y SQLite son alcanzables no demuestra que hayas clonado, subido o recuperado nada: prueba una subida real desde un cliente previsto.

## Límite de almacenamiento y recuperación

| Asignación | Ruta del contenedor | Contenido |
| --- | --- | --- |
| `gitea/data` | `/var/lib/gitea` | Base de datos SQLite, repositorios, objetos LFS, datos de la aplicación |
| `gitea/config` | `/etc/gitea` | `app.ini` y claves/configuración persistentes de la aplicación |

Ambos volúmenes con nombre pertenecen al contrato de datos y de copia de seguridad de la carga de trabajo. Una recuperación correcta detiene el único escritor de la aplicación, captura ambos volúmenes y los activa juntos con las escrituras detenidas: una copia en vivo del solo archivo SQLite no cumple ese contrato. Sigue [Copia de seguridad y restauración](/es/guides/stackkits/back-up-and-restore) para el ciclo de vida del espacio de trabajo. Gitea sin privilegios de root y con ellos usan disposiciones distintas, así que cambiar la imagen no es una migración de almacenamiento.

## Qué esperar

Gitea es un único servidor pequeño que usa SQLite en un nodo seleccionado. El inicio de sesión y las páginas de repositorios son rápidos para un hogar. Si la página carga pero la clonación falla, la causa habitual es la resolución de nombres o la confianza del certificado, no Gitea en sí.

## Si algo sale mal

- La clonación falla antes de pedir una contraseña: el nombre de host no se resuelve desde ese cliente, o el cliente no confía en el certificado de la CA interna.
- No recuerdas la contraseña del propietario: vuelve a revelarla con `stackkit secrets reveal --workload dev --slot owner-password`; el comando no crea ni restablece ninguna contraseña.
- La entrega falla por un administrador o una base de datos de usuarios existentes: no reemplaza cuentas ni restablece contraseñas; resuelve primero el conflicto de forma deliberada.
- Compara cualquier dirección con la salida del despliegue y consulta [Solución de problemas](/es/guides/stackkits/troubleshooting).

## Límites conocidos

- SSH no está expuesto; HTTPS nativo es la ruta de acceso Git documentada.
- Gitea Actions y los runners de CI no están instalados; la integración de runners todavía no tiene una ruta documentada.
- La recreación forzada del contenedor conserva el acceso del propietario, los metadatos de los repositorios privados y la configuración de la aplicación, pero el aprovisionamiento completo de un host Linux, la distribución real de DNS/CA en la LAN y un ciclo completo de copia de seguridad y restauración son niveles de evidencia separados y no se demuestran aquí.
