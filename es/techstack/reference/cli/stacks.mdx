## techstack api stacks create

Crea un despliegue de StackKit en el Homelab del propietario.

Crea un despliegue interno de StackKit bajo el Homelab único del propietario B2C autenticado a partir de la carga útil canónica de stack-spec de StackKits indicada como `stack_spec`. La ruta heredada `/stacks` y el campo de respuesta `stack_id` identifican ese despliegue; no crean ni seleccionan un segundo producto Homelab. Una instancia de TechStack puede servir a muchos propietarios, cada uno con su propio Homelab. Las cargas útiles heredadas `user_config`/kombination se siguen aceptando en este límite de compatibilidad. Los clientes del asistente deben enviar un `X-Idempotency-Key` estable; los reintentos con la misma clave y la misma carga útil devuelven el despliegue, el servidor planificado y el trabajo de aprovisionamiento originales.

```bash
techstack api stacks create [flags]
```

<Warning>Requiere confirmación. Esta operación crea el despliegue de StackKit e inicia el aprovisionamiento, que puede contratar servidores facturados. Pasa `--yes` o responde a la pregunta; una ejecución no interactiva sin `--yes` se detiene antes de cualquier solicitud con el código de salida 9.</Warning>

## techstack api stacks managed-runtimes add

Añade un Node gestionado mediante el control nativo del proveedor.

Crea o reanuda un trabajo determinista de Add-Server para el despliegue de StackKit propio exacto. El `Idempotency-Key` estándar es obligatorio. Repetir la misma clave con la misma solicitud canónica devuelve las correlaciones originales de trabajo, arrendamiento, servidor de runtime, generación de recursos y operación del proveedor; reutilizarla con otra intención falla con 409.

La clave sin procesar nunca se persiste ni se devuelve. Una respuesta perdida o un resultado incierto de la admisión nativa solo se puede reanudar con la misma clave. La aceptación HTTP significa que la admisión nativa es duradera y la reconciliación con el proveedor está pendiente; nunca afirma que la VM ya esté aprovisionada o sana. Una admisión nueva reserva de forma atómica la ranura de capacidad del tenant/propietario autenticado junto con la generación del arrendamiento y la operación del proveedor. Cuando la admisión nativa autorizada encuentra llena esa capacidad acotada, persiste un resultado 403 no reintentable, y repetir ese trabajo denegado devuelve el mismo resultado. Las repeticiones exactas de una admisión ya confirmada reutilizan su reserva existente. Esta versión no libera reservas automáticamente: un estado terminal o de baja local por sí solo no libera una ranura. El inventario de arrendamientos y los flags de entrega de funciones nunca autorizan ni deniegan capacidad. En el modo alojado, una admisión nueva también requiere los derechos comerciales de runtime y de proveedor firmados con v2, además de la decisión firmada de modo y límite `cloud.runtime.credits` `managed_servers`; los feature flags por sí solos nunca conceden capacidad del proveedor. El OSS autoalojado usa en su lugar su política estática de manifiesto de release, fijada en la construcción, sin depender de un derecho SaaS.

```bash
techstack api stacks managed-runtimes add <stack-id> [flags]
```

<Warning>Requiere confirmación. Esta operación contrata un servidor gestionado adicional para el despliegue de StackKit y se factura. Pasa `--yes` o responde a la pregunta; una ejecución no interactiva sin `--yes` se detiene antes de cualquier solicitud con el código de salida 9.</Warning>

## techstack api stacks resume-enrollment

Reanuda una espera vencida de un Node gestionado en su VM exacta existente.

Recuperación autenticada e idempotente de un trabajo persistido en `waiting_enrollment`, `waiting_provider_provision` o `waiting_canonical_guard` cuyo `next_resume_at` lleva vencido más allá del periodo de gracia acotado. El servidor valida el despliegue de StackKit propio, el trabajo de origen, el motivo de la espera, el arrendamiento exacto, el rol foundation activo y el Node canónico como una sola operación. Retira de forma atómica la espera de origen exacta, crea o rehidrata un único despliegue de sustitución determinista ligado al mismo arrendamiento y Node, y reproduce ese trabajo en llamadas posteriores. Antes de entrar en el handler, los workers de la cola adquieren de forma atómica la reclamación duradera de ejecución de compatibilidad `tenant/stack`; esto serializa distintos trabajos del mismo despliegue de StackKit entre réplicas de Techstack. La reclamación sigue en `running` de forma duradera hasta que el handler termina, también durante una cancelación. Este endpoint nunca invoca la creación de VM en el proveedor ni selecciona una VM más nueva. Una sustitución que se encuentra en `running` duradero tras un fallo sigue cerrada ante fallos, se informa como el mismo trabajo y nunca se duplica automáticamente; la reconciliación de acciones de runtime sigue siendo una tarea aparte del operador.

```bash
techstack api stacks resume-enrollment <stack-id> [flags]
```

| | |
| --- | --- |
| HTTP | `POST /api/v1/stacks/{id}/resume-enrollment` |
| Cambia el estado | Sí |
| Herramienta MCP | `resume_stack_enrollment` |

| Argumento | Tipo | Descripción |
| --- | --- | --- |
| `<stack-id>` | string | **Obligatorio.** ID del stack. |
| `--job-id` | string | **Obligatorio.** Trabajo de origen persistido que actualmente se proyecta como waiting_enrollment. |
| `--lease-id` | string | **Obligatorio.** Arrendamiento foundation gestionado exacto ya vinculado al trabajo de origen. |

## techstack api stacks routing ensure

Garantiza la capa de enrutamiento deseada para un despliegue de StackKit y un Node exactos.

Persiste de forma atómica una capa de enrutamiento idempotente y con revisiones sin modificar la intención inmutable del usuario. server_id siempre es exacto y obligatorio. lease_id es obligatorio para los runtimes gestionados y se omite para un runtime local/Basement, que no tiene arrendamiento. Para un destino gestionado, una solicitud con ensure_rollout en true despacha el pipeline de despliegue existente solo después de demostrar que su arrendamiento foundation activo seleccionado y su Node canónico coinciden con este destino exacto. La API nunca informa del trabajo resultante como ya aplicado. La capa solo se consume al derivar los artefactos de StackKits, y esta ruta nunca crea ni selecciona una VM de sustitución.

techstack api stacks routing ensure <stack-id> [flags]
