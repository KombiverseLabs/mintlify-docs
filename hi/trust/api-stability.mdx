kombify API `https://api.kombify.io` पर उपलब्ध है। यह पेज बताता है कि आप किन
राउट परिवारों पर भरोसा कर सकते हैं और kombify उन्हें कैसे बदलता है।

## स्थिरता वर्ग

हर राउट परिवार का एक वर्ग होता है। यह वर्ग API संदर्भ की ऑपरेशनों पर लागू होता
है। जो राउट संदर्भ में नहीं है, वह उस API का हिस्सा नहीं है जिस पर आप काम करते
हैं।

| वर्ग | आपके लिए इसका अर्थ |
| --- | --- |
| Stable | आप इस पर काम कर सकते हैं। यह API 1.0 रिलीज़ से स्थिर है: किसी संस्करण के भीतर बदलाव केवल जोड़ते हैं। |
| Protocol | संदेश एक साझा प्रोटोकॉल का पालन करते हैं (A2A, AG-UI, A2UI, MCP, Connect अनुबंध)। पथ और त्रुटि प्रारूप Stable की तरह स्थिर हैं; संदेशों की संरचना प्रोटोकॉल के अपने संस्करणों का पालन करती है। |
| Preview | प्रलेखित, पर इसके पीछे का उत्पाद अभी बदल सकता है। बदलाव रिलीज़ नोट्स में बिना किसी डेप्रिकेशन अवधि के सूचीबद्ध होते हैं। |

| वर्ग | राउट परिवार |
| --- | --- |
| Stable | `/v1/ai`, `/v1/embed`, `/v1/agents`, `/v1/orchestrator`, `/v1/homelab`, `/v1/speechkit`, `/v1/notifications`, `/v1/subdomains`, `/v1/content`, `/v1/connectors`, `/v1/harnesses`, `/v1/ril`, `/v1/decisions`, `/v1/supply-dock`, `/v2/supply-dock` |
| Protocol | `/a2a`, `/ag-ui`, `/a2ui`, `/v1/mcp/knowledge`, `/v1/connect` |

बाकी हर प्रलेखित राउट परिवार Preview है, जब तक यह पेज उसे सूचीबद्ध न करे।

## संस्करणीकरण

मुख्य संस्करण पथ का पहला खंड है, जैसे `/v1`। किसी संस्करण के भीतर ये बदलाव
योगात्मक हैं और कभी भी आ सकते हैं: नया राउट, नया वैकल्पिक अनुरोध फ़ील्ड, नया
प्रतिक्रिया फ़ील्ड, खुली प्रतिक्रिया सूची में नया मान, नया अस्वीकृति
`reason_code`। अपने क्लाइंट को ऐसा लिखें कि वह उन फ़ील्ड को अनदेखा करे जिन्हें
वह नहीं जानता।

ये बदलाव ब्रेकिंग हैं और केवल पुराने के बगल में नए मुख्य संस्करण के रूप में
आते हैं: स्वीकृत इनपुट को सँकरा करना, वैकल्पिक फ़ील्ड को अनिवार्य बनाना, किसी
फ़ील्ड का प्रकार या अर्थ बदलना, किसी मौजूदा परिणाम का स्थिति वर्ग बदलना, और
किसी मौजूदा कॉलर के लिए नई, प्रलेखित अस्वीकृति के बिना साइन-इन या
एंटाइटलमेंट आवश्यकताएँ कड़ी करना।

किसी संस्करण के भीतर राउट, फ़ील्ड या अस्वीकृति `reason_code` हटाना केवल नीचे
दिए डेप्रिकेशन क्रम से अनुमत है। सुरक्षा और कानूनी सुधार किसी अवधि के खत्म होने
से पहले अनुबंध तोड़ सकते हैं; तब रिलीज़ नोट यह बताता है और माइग्रेशन पथ देता
है।

स्वास्थ्य और खोज एंडपॉइंट (`/gateway/health`, `/.well-known/*`) बिना संस्करण के
हैं और योगात्मक नियम का पालन करते हैं। `/v1/blog` हटाया जा रहा है और स्थिरता के
दायरे में नहीं है।

## डेप्रिकेशन

Stable या Protocol वर्ग का राउट, फ़ील्ड या `reason_code` केवल इस क्रम के बाद
हटाया जाता है:

1. **घोषणा।** API संदर्भ उस ऑपरेशन को उसके उत्तराधिकारी के साथ डेप्रिकेटेड के
   रूप में चिह्नित करता है (फ़ील्ड या `reason_code` के लिए वह ऑपरेशन बताता है
   जो उसे लौटाता है), और रिलीज़ नोट उसका नाम लेता है। घोषणा एक सनसेट तिथि तय
   करती है।
2. **संकेत।** घोषणा करने वाले रिलीज़ से, डेप्रिकेटेड राउट `Deprecation` और
   `Sunset` हेडर तथा `rel="successor-version"` के साथ एक `Link` हेडर देता है जो
   प्रतिस्थापन की ओर इंगित करता है। फ़ील्ड या `reason_code` की घोषणा संदर्भ और
   रिलीज़ नोट में होती है।
3. **अवधि।** घोषणा और राउट हटाने के बीच कम से कम 180 दिन बीतते हैं, और फ़ील्ड
   या `reason_code` के लिए कम से कम 90 दिन। यदि सनसेट तिथि पर भी कॉलर इसका
   उपयोग करते हैं, तो तिथि आगे बढ़ जाती है।
4. **हटाना।** हटाने के बाद राउट `410` देता है और पथ मुक्त होने से पहले कम से कम
   एक और रिलीज़ तक अपने उत्तराधिकारी का नाम बताता है।

Preview राउट की कोई अवधि नहीं होती; उनका हटना फिर भी रिलीज़ नोट्स में आता है।

इसलिए कोई डेप्रिकेशन अवधि नहीं चलती। जब कोई घोषित होगी, तब ऊपर का क्रम लागू
होगा।
