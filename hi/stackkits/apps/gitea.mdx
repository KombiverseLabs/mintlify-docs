Gitea [Development](/hi/guides/stackkits/use-cases/development) यूज़ केस प्रदान करता है। Gitea वाला डेव वर्कलोड एक चुने गए नोड पर SQLite के साथ रूटलेस कंटेनर में निजी Git सर्वर चलाता है। सार्वजनिक पंजीकरण अक्षम है और नई रिपॉज़िटरी ज़बरदस्ती निजी बनती हैं। यह SSH को एक्सपोज़ नहीं करता, CI रनर इंस्टॉल नहीं करता और Actions सक्षम नहीं करता; अतिरिक्त उपयोगकर्ताओं और API टोकन के वर्कफ़्लो नेटिव Gitea ऑपरेशन ही रहते हैं। [यूज़-केस कैटलॉग](/hi/stackkits/reference/use-case-catalog) उन घटकों की सूची देता है जिन्हें प्रकाशित रिलीज़ घोषित करती है।

## यह क्या है

Gitea आपके कोड को रखने की एक निजी जगह है, जैसे कोड होस्टिंग वेबसाइट का छोटा, स्वयं चलाया जाने वाला संस्करण। आप सामान्य Git टूल से प्रोजेक्ट इसमें पुश करते हैं और उन्हें निजी रखते हैं। StackKit इसे इसलिए शामिल करता है ताकि आपकी रिपॉज़िटरी को किसी बाहरी प्रदाता के पास न रहना पड़े।

## कौन-से किट और यूज़ केस इसे शामिल करते हैं

Gitea, Dev यूज़ केस के Developer Platform हिस्से का डिफ़ॉल्ट एप्लिकेशन है। नीचे का उदाहरण स्टैंडअलोन Compose पर `basement-kit` का उपयोग करता है। [Development](/hi/guides/stackkits/use-cases/development) पेज की प्रमाण-स्थिति के अनुसार, यह चुना जा सकता है लेकिन अभी लाइफ़साइकिल-सत्यापित नहीं है।

## इसे कैसे खोलें

वह रूट खोलें जिसे आप वर्कलोड के लिए कॉन्फ़िगर करते हैं; उदाहरण में `https://dev.home.test` है। होस्टनेम को हर क्लाइंट से आपके होस्ट पर रिज़ॉल्व होना चाहिए, जैसा नीचे बताया गया है।

## डेव वर्कलोड को स्पष्ट रूप से चुनें

खाली ओनर वर्कस्पेस से Gitea चुनें और उसकी स्थानीय ओनर कस्टडी स्थापित करें:

```bash
stackkit init basement-kit --platform standalone-compose \
  --use-case dev --use-case-alternative dev=gitea \
  --use-case-alternative basement-core=standalone \
  --module-compute-profile stackkits-basement-core-runtime=standard \
  --module-compute-profile stackkits-gitea-runtime=standard \
  --owner-source local --owner-email owner@example.com --non-interactive
```

जनरेट करने से पहले, नीचे दिए गए फ़ील्ड को अपने [StackSpec](/hi/guides/stackkits/configure-stack-spec) के मौजूदा `capabilities`, `data` और `routes` सेक्शन में मर्ज करें। उनकी अन्य प्रविष्टियाँ बनाए रखें। यह अंश शुरुआती `home` साइट और `home-private` एक्सेस पॉलिसी का उपयोग करता है; उन संदर्भों, होम डोमेन और होस्ट स्टोरेज रूट को अपने वास्तविक होस्ट के अनुसार बदलें।

```yaml
capabilities:
  enable: [internal-pki]
data:
  bindings:
    dev:
      classes: [personal]
      primarySiteRef: home
routes:
  dev:
    serviceRef: dev
    moduleRef: stackkits-gitea-runtime
    exposure: local
    protocol: https
    port: 443
    targetPort: 3000
    host: dev.home.test
    path: /
    accessPolicyRef: home-private
```

उपयोगी नेटिव क्लोन URL के लिए Gitea को यह स्पष्ट HTTPS रूट और डेटा बाइंडिंग चाहिए। परिणाम को वैलिडेट और जनरेट करें:

```bash
stackkit validate
stackkit generate --local-node main --local-site home
```

फिर सामान्य डिलीवरी लाइफ़साइकिल का पालन करें: वैलिडेट करें, प्लान का निरीक्षण करें, और [समीक्षा, लागू और सत्यापित करें](/hi/guides/stackkits/review-plan-and-apply) में बताए अनुसार लागू और सत्यापित करें। देखी गई होस्ट इन्वेंटरी चुने गए मॉड्यूल प्रोफ़ाइल को पूरा करनी चाहिए; उदाहरण कॉन्फ़िगरेशन हार्डवेयर का प्रमाण नहीं है।

## नाम उपलब्ध कराएँ और रूट पर भरोसा करें

नेटिव HTTPS Git के लिए दो चीज़ें चाहिए, जिन्हें आपके होस्ट को पहले से पूरा करना होगा:

- रूट का होस्टनेम (उदाहरण में `dev.home.test`) हर उस क्लाइंट से उस होस्ट पर रिज़ॉल्व होना चाहिए जिससे आप क्लोन करना चाहते हैं।
- Git क्लाइंट को होस्ट के आंतरिक CA प्रमाणपत्र पर भरोसा करना होगा। क्लाइंट भरोसे के बिना HTTPS क्लोनिंग प्रमाणीकरण से पहले ही विफल हो जाती है।

## ओनर पासवर्ड प्रकट करें और साइन इन करें

पहली स्टार्टअप ट्रैफ़िक सर्व करने से पहले SQLite डेटाबेस माइग्रेट करती है और एडमिनिस्ट्रेटर `owner` बनाती है; ओनर ईमेल आपकी स्थानीय ओनर पहचान से आता है, और `owner-password` संदर्भ मौजूदा स्थानीय सीक्रेट कस्टडी में रखा जाता है। पासवर्ड को निजी टर्मिनल में पढ़ें:

```bash
stackkit secrets reveal --workload dev --slot owner-password
```

यह कमांड केवल मौजूदा वैलिडेट किए गए StackSpec में घोषित स्लॉट स्वीकार करता है, मान को stdout पर लिखता है — डिप्लॉयमेंट लॉग में कभी नहीं — और न पासवर्ड बनाता है न रीसेट करता है। कोई मौजूदा बेमेल एडमिनिस्ट्रेटर या बिना स्वामी वाला उपयोगकर्ता डेटाबेस डिलीवरी को विफल कर देता है, खातों को बदले या पासवर्ड रीसेट किए बिना।

## पहला उपयोग

1. ऊपर दिए कमांड से निजी टर्मिनल में ओनर पासवर्ड प्रकट करें।
2. Gitea रूट खोलें और `owner` के रूप में साइन इन करें।
3. एक निजी रिपॉज़िटरी बनाएँ।
4. उसका HTTPS क्लोन URL कॉपी करें और अपने नेटिव Git क्रेडेंशियल स्टोरेज का उपयोग करते हुए किसी वास्तविक क्लाइंट से क्लोन करें।
5. एक छोटा टेस्ट कमिट पुश करें।

`owner` के रूप में साइन इन करें, निजी रिपॉज़िटरी बनाएँ, और अपने नेटिव Git क्रेडेंशियल स्टोरेज के साथ उसके HTTPS क्लोन URL का उपयोग करें। Git सीधे Gitea से प्रमाणित होता है: कोई ब्राउज़र फ़ॉरवर्ड-ऑथ गेट Git अनुरोधों को नहीं रोकता। जो रेडीनेस केवल यह बताती है कि HTTP प्रोसेस और SQLite पहुँच में हैं, वह यह साबित नहीं करती कि आपने कुछ क्लोन, पुश या रिकवर किया है — किसी इच्छित क्लाइंट से वास्तविक पुश का परीक्षण करें।

## स्टोरेज और रिकवरी की सीमा

| आवंटन | कंटेनर पाथ | सामग्री |
| --- | --- | --- |
| `gitea/data` | `/var/lib/gitea` | SQLite डेटाबेस, रिपॉज़िटरी, LFS ऑब्जेक्ट, एप्लिकेशन डेटा |
| `gitea/config` | `/etc/gitea` | `app.ini` और सहेजी गई एप्लिकेशन कुंजियाँ/कॉन्फ़िगरेशन |

दोनों नामित वॉल्यूम वर्कलोड के डेटा और बैकअप कॉन्ट्रैक्ट का हिस्सा हैं। सही रिकवरी एप्लिकेशन के एकल राइटर को शांत करती है, दोनों वॉल्यूम कैप्चर करती है, और राइट रोककर उन्हें साथ में सक्रिय करती है — केवल SQLite फ़ाइल की लाइव कॉपी वह कॉन्ट्रैक्ट नहीं है। वर्कस्पेस लाइफ़साइकिल के लिए [बैकअप और रिस्टोर](/hi/guides/stackkits/back-up-and-restore) का पालन करें। रूटलेस और रूटफ़ुल Gitea अलग-अलग लेआउट उपयोग करते हैं, इसलिए इमेज बदलना स्टोरेज माइग्रेशन नहीं है।

## क्या अपेक्षा करें

Gitea एक चुने गए नोड पर SQLite का उपयोग करने वाला एकल छोटा सर्वर है। एक घर के लिए साइन-इन और रिपॉज़िटरी पेज तेज़ हैं। यदि पेज लोड होता है लेकिन क्लोनिंग विफल होती है, तो आमतौर पर कारण नाम रिज़ॉल्यूशन या प्रमाणपत्र पर भरोसा होता है, Gitea स्वयं नहीं।

## कुछ गड़बड़ हो तो

- क्लोनिंग पासवर्ड माँगने से पहले विफल हो जाती है: होस्टनेम उस क्लाइंट से रिज़ॉल्व नहीं होता, या क्लाइंट आंतरिक CA प्रमाणपत्र पर भरोसा नहीं करता।
- आपको ओनर पासवर्ड याद नहीं: `stackkit secrets reveal` से उसे फिर प्रकट करें; यह कमांड न पासवर्ड बनाता है न रीसेट करता है।
- मौजूदा एडमिनिस्ट्रेटर या उपयोगकर्ता डेटाबेस पर डिलीवरी विफल होती है: यह खातों को नहीं बदलती और न पासवर्ड रीसेट करती है; पहले टकराव को सोच-समझकर सुलझाएँ।
- किसी भी पते को रोलआउट आउटपुट से मिलाएँ और [समस्या निवारण](/hi/guides/stackkits/troubleshooting) देखें।

## ज्ञात सीमाएँ

- SSH एक्सपोज़ नहीं है; नेटिव HTTPS ही प्रलेखित Git एक्सेस पथ है।
- Gitea Actions और CI रनर इंस्टॉल नहीं हैं; रनर इंटीग्रेशन का अभी कोई प्रलेखित पथ नहीं है।
- ज़बरदस्ती कंटेनर पुनः बनाने पर ओनर एक्सेस, निजी रिपॉज़िटरी मेटाडेटा और एप्लिकेशन कॉन्फ़िगरेशन बने रहते हैं, लेकिन पूर्ण Linux होस्ट प्रोविज़निंग, वास्तविक LAN DNS/CA वितरण और पूर्ण बैकअप/रिस्टोर चक्र अलग प्रमाण स्तर हैं और यहाँ सिद्ध नहीं हैं।
