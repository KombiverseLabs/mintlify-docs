
## stackkit host attach-conformance

प्लान जनरेशन से पहले सटीक होस्ट प्रमाण को Inventory से जोड़ें।

```bash
stackkit host attach-conformance [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--binding` | string | — | **आवश्यक।** वर्कस्पेस तक सीमित ExternalHostBinding JSON |
| `--inventory` | string | — | **आवश्यक।** वर्कस्पेस तक सीमित inventory.json, जिसे परमाणु रूप से अपडेट करना है |
| `--receipt` | string | — | **आवश्यक।** वर्कस्पेस तक सीमित HostConformanceReceipt JSON |

## stackkit host conformance

इस होस्ट पर प्रदाता-निरपेक्ष अनुरूपता रसीद बनाएँ।

```bash
stackkit host conformance [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--binding` | string | — | **आवश्यक।** स्थानीय ExternalHostBinding JSON फ़ाइल |
| `--output, -o` | string | `-` | रसीद का गंतव्य (stdout पर JSON के लिए '-') |

## stackkit host delivery

इस नोड का सीलबंद होस्ट डिलीवरी रिसिपिएंट प्रबंधित करें।

सीलबंद होस्ट डिलीवरी इस नोड तक Wallet आइटम, बैकअप लक्ष्य और SSH एक्सेस पहुँचाती है। डिलीवर करने वाला प्राधिकार हर मान को इस नोड की रिसिपिएंट की (HPKE, pkg/hostdelivery) से सील करता है; केवल यह नोड उसे अपनी कस्टडी में खोलता है। Techstack और Guard केवल सिफ़रटेक्स्ट और संदर्भ वहन करते हैं।

```bash
stackkit host delivery [flags]
```

उप-कमांड: [`stackkit host delivery detach`](#stackkit-host-delivery-detach), [`stackkit host delivery recipient`](#stackkit-host-delivery-recipient), [`stackkit host delivery status`](#stackkit-host-delivery-status)

### stackkit host delivery detach

इस नोड पर होस्ट डिलीवरी रोकें और रोटेट किए जाने वाले डिलीवर किए गए सीक्रेट सूचीबद्ध करें।

इस नोड को होस्ट डिलीवरी से अलग करें: हर डिलीवर किया गया सीक्रेट रोटेशन-आवश्यक चिह्नित होता है, रिटायर रिसिपिएंट कीज़ नष्ट होती हैं, और जब तक नोड को 'host delivery recipient `--rotate`' से दोबारा नामांकित नहीं किया जाता, कोई डिलीवरी नहीं खुलती। परिणाम रोटेट किए जाने वाले संदर्भ और संस्करण वहीं सूचीबद्ध करता है जहाँ से वे आए थे; उसमें कभी कोई मान नहीं होता। स्थानीय कस्टडी में पहले से मौजूद मान यहाँ उपयोग योग्य रहते हैं।

```bash
stackkit host delivery detach [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--owner-approve` | bool | — | इस नोड को अलग करने को अधिकृत करें |

**उदाहरण**

```bash
stackkit host delivery detach --owner-approve
```

### stackkit host delivery recipient

इस नोड की रिसिपिएंट की प्रमाणित करें, डिलीवर करने वाला प्राधिकार पिन करें, या की रोटेट करें।

स्थानीय Owner की से हस्ताक्षरित एक कथन प्रिंट करें जो इस नोड की रिसिपिएंट की और उसकी जनरेशन को इस Site और नोड से बाँधता है तथा कॉलर की चुनौती को दोहराता है। प्राइवेट की स्थानीय कस्टडी से बाहर कभी नहीं जाती।

`--authority-key` वर्तमान जनरेशन के लिए डिलीवर करने वाले प्राधिकार की Ed25519 पब्लिक की पिन करता है; Wallet आइटम और SSH एक्सेस केवल उसी से हस्ताक्षरित होने पर खुलते हैं। पिन की गई की कभी जगह पर नहीं बदली जाती। `--rotate` नोड को अगली जनरेशन में दोबारा नामांकित करता है (और `--authority-key` के साथ नया प्राधिकार पिन करता है): पिछली की रोटेशन से पहले जारी डिलीवरी को उनकी अधिकतम 15 मिनट की आयु तक खोलती है और फिर नष्ट कर दी जाती है। रोटेशन detach को भी समाप्त करता है।

```bash
stackkit host delivery recipient [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--authority-key` | string | — | इस जनरेशन के लिए पिन की जाने वाली डिलीवर करने वाले प्राधिकार की Ed25519 पब्लिक की (base64) |
| `--authority-key-id` | string | — | वह Key ID जिससे डिलीवर करने वाला प्राधिकार envelopes पर हस्ताक्षर करता है |
| `--challenge` | string | — | डिलीवर करने वाले प्राधिकार का ताज़ा मान जिसे कथन में दोहराना होगा |
| `--owner-approve` | bool | — | इस नोड के रिसिपिएंट बदलाव को अधिकृत करें |
| `--rotate` | bool | — | अगली रिसिपिएंट जनरेशन में दोबारा नामांकित करें |

**उदाहरण**

```bash
stackkit host delivery recipient --challenge "$CHALLENGE" --authority-key "$WALLET_KEY" --authority-key-id wallet-1 --owner-approve
stackkit host delivery recipient --challenge "$CHALLENGE" --rotate --owner-approve
```

### stackkit host delivery status

रिसिपिएंट जनरेशन, पिन किया गया प्राधिकार, detach स्थिति और डिलीवर किए गए संदर्भ दिखाएँ।

इस नोड की रिसिपिएंट जनरेशन और फ़िंगरप्रिंट, अब भी खुलने योग्य रिटायर जनरेशन, पिन किया गया डिलीवर करने वाला प्राधिकार, नोड detached है या नहीं, और हर डिलीवर किया गया सीक्रेट संदर्भ और संस्करण के अनुसार उसके रोटेशन चिह्न सहित रिपोर्ट करें। कोई मान नहीं पढ़ा जाता।

```bash
stackkit host delivery status [flags]
```

## stackkit host environment

देखें कि यह होस्ट होम नेटवर्क जैसा दिखता है या सार्वजनिक सर्वर जैसा।

इस मशीन का नेटवर्क परिवेश पहचानें।

यह अवलोकन है, kit का चयन नहीं। इंस्टॉलर और init इसका उपयोग VPS पर स्थानीय होम पते या LAN होस्ट पर Cloud Kit बनाने से पहले पूछने के लिए करते हैं। STACKKIT_NETWORK_ENV=home|vps|cloud|unknown लाइव पहचान को ओवरराइड करता है।

```bash
stackkit host environment [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--json` | bool | — | अवलोकन को JSON के रूप में जारी करें |

**उदाहरण**

```bash
# Show whether this host looks like a home network or a public server
stackkit host environment

# The same observation as JSON
stackkit host environment --json

# Override a wrong detection for the next command, here Basement Kit init on a home host
STACKKIT_NETWORK_ENV=home stackkit init basement-kit --catalog-defaults --owner-source=local --owner-email you@example.com
```

## stackkit host gpu-check

Prove the NVIDIA GPU under a short real CUDA load.

Run NVIDIA's CUDA vectorAdd sample in a container on the GPU (Docker CDI device nvidia.com/gpu=all), then read the kernel log for NVRM Xid errors and ask nvidia-smi again.

nvidia-smi listing the GPU is not proof that it works: a GPU on a weak power supply or a marginal link, typical for a Thunderbolt eGPU, answers at idle and falls off the bus (Xid 79) as soon as CUDA draws power. This check refuses then and names the cause.

It changes nothing on the host except pulling the pinned sample image. Run it as root so the kernel log can be read.

```bash
stackkit host gpu-check [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--image` | string | `nvcr.io/nvidia/k8s/cuda-sample:vectoradd-cuda12.5.0@sha256:7c7540bdf1f942d4fb6db97069fd6c289471b54ac29e3c7fcdf914cf77af7d41` | CUDA sample image that prints "Test PASSED" |
| `--json` | bool | — | Emit the check and its evidence as machine-readable JSON |
| `--runs` | int | `10` | How many times the CUDA sample runs |

**Examples**

```bash
# Prove the GPU after the driver and Container Toolkit are installed
sudo stackkit host gpu-check

# Longer load, machine-readable result
sudo stackkit host gpu-check --runs 50 --json
```

## stackkit host migrate-browser-ca

इस नोड के प्रमाणित लेगेसी CA को ब्राउज़र-सक्षम नीति में माइग्रेट करें।

लेगेसी Basement CA साइनिंग कीज़ को स्पष्ट रूप से माइग्रेट करें, जबकि Owner साइनिंग की, PocketID पहचानें, रनटाइम सीक्रेट, ingress लीफ़ कीज़, पते और वॉल्यूम सुरक्षित रहते हैं। पहले से वर्तमान root को बनाए रखें। `--complete` से पहले वर्तमान नेटिव प्लान लागू और सत्यापित करें। बदली हुई सार्वजनिक root को क्लाइंट मौजूदा client-trust हैंडऑफ़ के ज़रिए स्वीकृत करें।

```bash
stackkit host migrate-browser-ca [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--complete` | bool | — | वर्तमान नेटिव Apply और सामान्य TLS सत्यापन के बाद रिकवरी जर्नल रिटायर करें |
| `--owner-approve` | bool | — | इस नोड के स्पष्ट CA संक्रमण को अधिकृत करें |

## stackkit host preflight

जाँचें कि यह होस्ट चुना गया StackKit चला सकता है या नहीं।

इस होस्ट को मापें और kit द्वारा घोषित न्यूनतम सीमा से तुलना करें।

Preflight केवल रीड-ओनली जाँच करता है: यह कभी कुछ इंस्टॉल, शुरू या कॉन्फ़िगर नहीं करता। Apply होस्ट में बदलाव करने से पहले यही प्रवेश-जाँच चलाता है।

```bash
stackkit host preflight [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--json` | bool | — | वर्ज़न वाली preflight रिपोर्ट को मशीन-पठनीय JSON के रूप में जारी करें |
| `--local-node` | string | — | दिए गए ResolvedPlan में सटीक स्थानीय Node |
| `--policy` | string | — | प्रवेश नीति: strict, warn (डिफ़ॉल्ट) या skip |
| `--resolved-plan` | string | — | सत्यापित कैनोनिकल ResolvedPlan जिसके होस्ट लिसनर जाँचने हैं |

**उदाहरण**

```bash
# Check this host against the kit selected in the current deployment directory
stackkit host preflight

# Also refuse on warnings and unknown facts, and print the report as JSON
stackkit host preflight --policy strict --json
```

## stackkit host prepare

Cloud Kit apply से पहले इस होस्ट को तैयार करें।

होस्ट-सुरक्षा द्वारा root लॉगिन बंद करने से पहले ज़रूरी Cloud निष्पादन-चैनल अकाउंट और SSH की कस्टडी प्रोविज़न करें।

Cloud Kit इंस्टॉलर और apply इसे स्वतः कॉल करते हैं। यह कमांड डायग्नोस्टिक के लिए और मैन्युअल रुकावट के बाद वर्कस्पेस को कन्वर्ज करने के लिए है। यह .stackkit/cloud-host-security/execution-channel/ के अंतर्गत वर्कस्पेस-कस्टडी वाली की बनाती या दोबारा उपयोग करती है और मिलती-जुलती पब्लिक की को निष्पादन-चैनल Linux अकाउंट पर इंस्टॉल करती है।

```bash
stackkit host prepare [flags]
```

**उदाहरण**

```bash
# Converge the execution-channel account after an interrupted Cloud Kit install (run as root in the Cloud Kit deployment directory)
cd my-cloud
stackkit host prepare
```

## stackkit host reboot

इस नोड का रीबूट शेड्यूल करें।

थोड़ी देरी के बाद इस नोड का रीबूट शेड्यूल करें और तुरंत लौट आएँ।

लौटाया गया boot_id_before वर्तमान बूट की पहचान करता है, ताकि कॉलर अलग boot ID पढ़कर जान सके कि नोड वापस आ गया। कमांड उस नोड को अस्वीकार करती है जो Techstack कंट्रोल प्लेन चलाता है, जहाँ apt या dpkg लॉक रखता है या होस्ट अपडेट चल रहा है, और जो बिना निगरानी बूट नहीं हो सकता (/etc/crypttab में ऐसे वॉल्यूम जिन्हें पासफ़्रेज़ चाहिए, या apt नहीं है)।

देरी समाप्त होने पर एक गार्ड फिर जाँचता है, किसी भी पैकेज ऑपरेशन के पूरा होने के लिए 15 मिनट तक प्रतीक्षा करता है और dpkg लॉक पकड़े हुए रीबूट का अनुरोध करता है। जो नोड व्यस्त रहता है उसे रीबूट नहीं किया जाता; उसकी boot ID वही रहती है।

```bash
stackkit host reboot [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--delay` | duration | `30s` | रीबूट शुरू होने तक का समय (1s से 5m) |
| `--json` | bool | — | stackkit.host-maintenance/v1 परिणाम को मशीन-पठनीय JSON के रूप में जारी करें |
| `--yes` | bool | — | पुष्टि करें कि यह नोड रीबूट हो सकता है |

**उदाहरण**

```bash
# Reboot this node in 30 seconds
sudo stackkit host reboot --yes

# Reboot in two minutes and report the boot ID to compare against
sudo stackkit host reboot --yes --delay 2m --json
```

## stackkit host remediate

होस्ट preflight में मिली समस्याओं के सुधार दिखाएँ या लागू करें।

इस होस्ट के preflight निष्कर्षों के सुधार सूचीबद्ध करें, या उनमें से एक लागू करें।

`--apply` के बिना कुछ नहीं बदलता: कमांड होस्ट को मापती है और प्रिंट करती है कि हर सुधार क्या करेगा, क्या उसे पूर्ववत किया जा सकता है और क्या उसे root चाहिए।

`--apply` &lt;id&gt; `--yes` के साथ नामित सुधार चलता है, और जिस जाँच ने उसे उचित ठहराया था उसे बाद में फिर मापा जाता है, ताकि परिणाम बताए कि वास्तव में क्या बदला, न कि सिर्फ़ यह कि कोशिश की गई।

```bash
stackkit host remediate [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--apply` | string | — | नामित समाधान लागू करें (`--yes` आवश्यक) |
| `--auto-reversible` | bool | — | हर वह पूर्ववत करने योग्य सुधार लागू करें जो बिना निगरानी चल सकता है (`--yes` आवश्यक) |
| `--json` | bool | — | सुधार प्लान या रिकॉर्ड को मशीन-पठनीय JSON के रूप में जारी करें |
| `--policy` | string | — | निष्कर्ष खोजने के लिए उपयोग की गई preflight नीति: strict या warn (डिफ़ॉल्ट) |
| `--yes` | bool | — | पुष्टि करें कि नामित समाधान इस होस्ट को बदल सकता है |

**उदाहरण**

```bash
# List the fixes for this host's preflight findings without changing anything
stackkit host remediate

# Carry out one fix by the ID the list printed
stackkit host remediate --apply <resolution-id> --yes

# Carry out every undoable fix that may run unattended
stackkit host remediate --auto-reversible --yes
```

## stackkit host security

वर्ज़नयुक्त साक्ष्य के साथ होस्ट सुरक्षा आधाररेखा सत्यापित और ठीक करें।

इस नोड को StackKits होस्ट सुरक्षा आधाररेखा के अनुसार जाँचें और प्रबंधन पथ काटे बिना भटके हुए नियंत्रण बहाल करें।

'verify' होस्ट को कभी नहीं बदलता। यह फ़ायरवॉल, sshd, ब्रूट-फ़ोर्स सुरक्षा, स्वचालित और लंबित सुरक्षा अपडेट, रीबूट स्थिति, कर्नेल पैरामीटर, खुले listeners और प्रमाणपत्र की समाप्ति के लिए, और (एक बार दर्ज होने पर) इस नोड को डिलीवर किए गए SSH CA ट्रस्ट और होस्ट सर्टिफ़िकेट ('host ssh apply') के लिए stackkit.host-security-evidence/v1 बनाता है। हर नियंत्रण compliant, drifted, unknown या ओनर द्वारा स्वीकृत अपवाद होता है, और साक्ष्य की समय-सीमा समाप्त होती है: पुराना अवलोकन unknown होता है और unknown नियंत्रण कभी compliant नहीं माना जाता।

यह अपने आप (Standard Mode, बिना अकाउंट) और Techstack द्वारा डिप्लॉयमेंट प्रबंधित किए जाने पर पिन की गई CLI के माध्यम से (`--mode` advanced) काम करता है।

```bash
stackkit host security [flags]
```

उप-कमांड: [`stackkit host security repair`](#stackkit-host-security-repair), [`stackkit host security status`](#stackkit-host-security-status), [`stackkit host security verify`](#stackkit-host-security-verify)

### stackkit host security repair

प्रबंधन पथ काटे बिना भटके हुए आधाररेखा नियंत्रण बहाल करें।

भटके हुए नियंत्रण की बहाली की योजना बनाएँ, या `--apply` के साथ उसे पूरा करें।

`--apply` के बिना कुछ नहीं बदलता: कमांड होस्ट को मापता है और बताता है कि हर सुधार क्या करेगा। `--apply` के साथ केवल नामित (`--control`) या drifted नियंत्रण छुए जाते हैं, और हर बदलाव को पहले जाँचा जाता है:

```text
  - the firewall always keeps admitting the ssh sessions in use and every
    --management-source on every sshd port, and a policy that would not is
    refused before it is loaded;
  - password logins are disabled only when an account holds an authorized key;
    without one they stay on, the step is refused with reason no_authorized_key
    and the rest of the baseline is still repaired. The previous sshd and
    firewall configuration is restored if the new one does not validate or does
    not take effect;
  - fail2ban never bans the management path.
```

जिस नियंत्रण को देखा नहीं जा सकता या जिसके लिए ओनर ने अपवाद स्वीकृत किया है, उसे छुआ नहीं जाता। Cloud Site का फ़ायरवॉल और root लॉगिन 'stackkit apply' द्वारा बहाल किए जाते हैं। हर चरण नियंत्रण की पहले और बाद की स्थिति दर्ज करता है, और compliant नियंत्रण पर दोबारा repair करने से कुछ नहीं बदलता।

```bash
stackkit host security repair [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--apply` | bool | — | repair पूरा करें; इसके बिना कमांड केवल योजना बनाता है |
| `--control` | stringArray | — | repair को इस नियंत्रण ID तक सीमित करें (दोहराया जा सकता है) |
| `--declared-port` | stringArray | — | tcp/443 या udp/5353 के रूप में घोषित सेवा पोर्ट (दोहराया जा सकता है) |
| `--exceptions` | string | `/etc/stackkit/host-security/exceptions.json` | ओनर-नियंत्रित अपवाद फ़ाइल (हर अपवाद के लिए ओनर और समाप्ति आवश्यक है) |
| `--freshness` | duration | `15m0s` | साक्ष्य की समय-सीमा समाप्त होने से पहले उस पर भरोसे की अवधि (1m से 24h) |
| `--host-name` | stringArray | — | वह नाम जो डिलीवर किए गए SSH होस्ट सर्टिफ़िकेट में होना चाहिए (दोहराने योग्य; डिफ़ॉल्ट: सिस्टम होस्टनाम) |
| `--json` | bool | — | परिणाम मशीन-पठनीय JSON में जारी करें |
| `--kit` | string | — | दर्ज किया जाने वाला Kit slug (डिफ़ॉल्ट: वर्कस्पेस StackSpec का Kit) |
| `--local-node` | string | — | दिए गए ResolvedPlan का सटीक स्थानीय Node |
| `--management-source` | stringArray | — | वह नेटवर्क जिसे हमेशा ssh तक पहुँचना चाहिए, CIDR के रूप में (दोहराया जा सकता है) |
| `--mode` | string | `standard` | दर्ज किया जाने वाला लाइफ़साइकिल मोड: standard, या Techstack द्वारा यह डिप्लॉयमेंट प्रबंधित होने पर advanced |
| `--no-record` | bool | — | repair के बाद का साक्ष्य .stackkit/ के अंतर्गत न लिखें |
| `--resolved-plan` | string | — | सत्यापित कैनोनिकल ResolvedPlan, जिसके घोषित listeners के अनुसार एक्सपोज़र का आकलन किया जाए |
| `--site-kind` | string | — | इस होस्ट का Site प्रकार: home या cloud (डिफ़ॉल्ट: Kit से अनुमानित; modern-homelab के लिए आवश्यक) |

**उदाहरण**

```bash
# See what would be repaired
sudo stackkit host security repair --site-kind home

# Restore only the firewall, keeping a jump host reachable
sudo stackkit host security repair --apply --control firewall.default_inbound --management-source 198.51.100.0/24
```

## stackkit host ssh

इस नोड तक डिलीवर किया गया SSH सर्टिफ़िकेट एक्सेस।

```bash
stackkit host ssh [flags]
```

उप-कमांड: [`stackkit host ssh apply`](#stackkit-host-ssh-apply)

### stackkit host ssh apply

stdin से सीलबंद SSH CA ट्रस्ट, रिवोकेशन या होस्ट सर्टिफ़िकेट डिलीवरी लागू करें।

stdin पर एक सीलबंद ssh-ca-trust, ssh-ca-revoke या ssh-host-certificate envelope पढ़ें, जो पिन किए गए डिलीवर करने वाले प्राधिकार से हस्ताक्षरित हो, और उसे इस सर्वर के sshd पर लागू करें:

```text
  - ssh-ca-trust installs the owner's user CA keys as TrustedUserCAKeys
    (/etc/ssh/stackkit/trusted_user_ca_keys) and one AuthorizedPrincipalsFile
    per local user (/etc/ssh/stackkit/principals/<user>). Root is never a
    target. An empty key list revokes like ssh-ca-revoke.
  - ssh-ca-revoke removes that trust. Revocations take effect at once and are
    never rolled back; one sshd cannot reload for is recorded as cleanup
    pending and finished by 'host security repair'.
  - ssh-host-certificate installs a host certificate beside the host key it
    certifies, only if it names every --host-name (default: the system
    hostname) and is currently valid.
```

sshd केवल तब reload होता है जब 'sshd -t' नया कॉन्फ़िगरेशन स्वीकार कर ले; विफल बदलाव रोलबैक हो जाता है। लागू स्थिति owner कस्टडी में दर्ज होती है, इसलिए 'host security verify' drift रिपोर्ट करता है और 'host security repair' उसे दोबारा इंस्टॉल करता है।

```bash
stackkit host ssh apply [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--host-name` | stringArray | — | वह नाम जो होस्ट सर्टिफ़िकेट में principal के रूप में होना चाहिए (दोहराने योग्य; डिफ़ॉल्ट: सिस्टम होस्टनाम) |
| `--owner-approve` | bool | — | इस सर्वर का SSH एक्सेस बदलने को अधिकृत करें |
| `--tenant-ref` | string | — | वह tenant जिसे सीलबंद डिलीवरी संबोधित होनी चाहिए |

**उदाहरण**

```bash
sudo stackkit host ssh apply --tenant-ref "$TENANT" --owner-approve < envelope.json
```

## stackkit host updates

इस नोड पर ऑपरेटिंग-सिस्टम पैकेज अपडेट प्लान करें और लागू करें।

इस Debian या Ubuntu नोड पर ऑपरेटिंग-सिस्टम पैकेज अपडेट प्लान करें और लागू करें।

कंटेनर रनटाइम (docker.io, docker-ce\*, containerd\*, runc) होल्ड पर है: वह प्लान में सूचीबद्ध है पर apply उसे कभी इंस्टॉल नहीं करता, क्योंकि उसे अपग्रेड करने से हर वर्कलोड रीस्टार्ट होता है। Apply कभी पैकेज नहीं हटाता, autoremove नहीं चलाता और रीबूट नहीं करता; उसके लिए 'stackkit host reboot' उपयोग करें।

```bash
stackkit host updates [flags]
```

उप-कमांड: [`stackkit host updates apply`](#stackkit-host-updates-apply), [`stackkit host updates plan`](#stackkit-host-updates-plan)

### stackkit host updates apply

ठीक वही समीक्षित अपडेट प्लान इंस्टॉल करें।

समीक्षित 'stackkit host updates plan' द्वारा रिपोर्ट किया गया पैकेज सेट ठीक वैसा ही इंस्टॉल करें।

लंबित सेट को पहले फिर सिमुलेट किया जाता है; उसका डाइजेस्ट `--plan-digest` से अलग होने पर कुछ इंस्टॉल नहीं होता (plan_stale)। apt एक अस्थायी systemd यूनिट (kombify-host-update-\*) में बिना इंटरैक्शन चलता है और मौजूदा कॉन्फ़िगरेशन फ़ाइलें रखता है, इसलिए CLI या एजेंट टाइमआउट केवल प्रतीक्षा रोकता है, dpkg को कभी नहीं। परिणाम हर पैकेज का पहले और बाद का वर्ज़न और यह दर्ज करता है कि नोड को अब रीबूट चाहिए या नहीं।

```bash
stackkit host updates apply [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--json` | bool | — | stackkit.host-maintenance/v1 परिणाम को मशीन-पठनीय JSON के रूप में जारी करें |
| `--plan-digest` | string | — | **आवश्यक।** समीक्षित प्लान का plan_digest (sha256:&lt;hex&gt;) |
| `--yes` | bool | — | पुष्टि करें कि प्लान किए गए पैकेज इंस्टॉल किए जा सकते हैं |

**उदाहरण**

```bash
# Apply the plan you reviewed
sudo stackkit host updates apply --plan-digest sha256:<digest> --yes
```

### stackkit host updates plan

पैकेज इंडेक्स रीफ़्रेश करें और लंबित अपडेट दिखाएँ।

पैकेज इंडेक्स रीफ़्रेश करें और दिखाएँ कि 'stackkit host updates apply' क्या इंस्टॉल करेगा।

परिणाम हर लंबित पैकेज को उसके वर्तमान और नए वर्ज़न के साथ, होल्ड पर रखे कंटेनर-रनटाइम पैकेज, apt द्वारा रोके गए पैकेज, रीबूट की संभावना (kernel, C library या systemd) और dpkg समस्याएँ सूचीबद्ध करता है। plan_digest सटीक पैकेज सेट को बाँधता है; मेल न खाने पर apply मना कर देता है।

```bash
stackkit host updates plan [flags]
```

| Flag | प्रकार | डिफ़ॉल्ट | विवरण |
| --- | --- | --- | --- |
| `--json` | bool | — | stackkit.host-maintenance/v1 परिणाम को मशीन-पठनीय JSON के रूप में जारी करें |

**उदाहरण**

```bash
# Show the pending updates of this node
```
