रिलीज़ किए गए Basement Kit में स्थानीय, ओनर-नियंत्रित Kopia बैकअप लाइफ़साइकल शामिल है। इसे केवल उसी लागू किए गए StackKits वर्कस्पेस से चलाएँ जिसके डेटा को आप सुरक्षित रखना चाहते हैं।

रीस्टोर अभ्यास को सेटअप का हिस्सा बनाएँ, बाद का काम नहीं।

## महत्वपूर्ण डेटा इम्पोर्ट करने से पहले रिकवरी का अभ्यास करें

1. Basement Kit को लागू करें और सत्यापित करें।
2. पुष्टि करें कि प्राथमिक डेटा और बैकअप रूट अलग-अलग हैं।
3. नीचे दिए गए कमांड से रिपॉज़िटरी कॉन्फ़िगर करें और एक स्नैपशॉट बनाएँ।
4. उस स्नैपशॉट को आइसोलेटेड स्टेजिंग में रीस्टोर करें और नतीजे की समीक्षा करें।
5. किसी भी एक्टिवेशन के बाद सेवाओं को फिर से सत्यापित करें। रिकवरी के बाद का सत्यापन स्नैपशॉट जितना ही मायने रखता है।

स्टोरेज, वर्कलोड या रिलीज़ में बड़े बदलाव के बाद अभ्यास दोहराएँ।

## रिपॉज़िटरी कॉन्फ़िगर करें और जाँचें

```bash
stackkit backup configure --json
stackkit backup status --json
```

रिपॉज़िटरी, सोर्स सेट, बहिष्करण और स्थानीय कस्टडी हल किए गए प्लान से निकाले जाते हैं। कमांड को किसी मनमाने वॉल्यूम पर न चलाएँ और न ही ओनर कस्टडी को बायपास करें।

### स्नैपशॉट में क्या शामिल है

प्लान का `backupPolicy.coverage` चुनता है कि स्नैपशॉट डेटा की कौन-सी श्रेणियाँ लेगा। तीन नेस्टेड समूह हैं, और जिस स्टैक के पीछे कोई सब्सक्रिप्शन नहीं है वह `content` पर हल होता है:

| कवरेज | यह क्या चुनता है |
| --- | --- |
| `config` | स्टैक कॉन्फ़िगरेशन, सीक्रेट सामग्री, प्लेटफ़ॉर्म स्टेट, सर्वरलेस कॉन्फ़िगरेशन |
| `content` | ऊपर का सब कुछ, साथ में डेटाबेस, उपयोगकर्ता सामग्री, दस्तावेज़ और टेलीमेट्री टाइम सीरीज़ |
| `media` | ऊपर का सब कुछ, साथ में फ़ोटो के ओरिजिनल और बड़ी मीडिया फ़ाइलें |

Media चुना जाता है, विरासत में नहीं मिलता। फ़ोटो और वीडियो लाइब्रेरी रिपॉज़िटरी में सबसे ज़्यादा जगह लेती हैं, इसलिए पहला सीड चुपचाप उन्हें नहीं खींचेगा: जब चाहें तब `media` चुनें।

ऊपर का स्टेटस आउटपुट लागू की गई कॉन्फ़िगरेशन द्वारा चुने गए सटीक वॉल्यूम और बहिष्करण बताता है, जो "अगले स्नैपशॉट में क्या होगा" का उत्तर है। कवरेज समूह वह है जो प्लान ने माँगा था; स्टेटस आउटपुट वह है जिस पर एक लागू की गई कॉन्फ़िगरेशन हल हुई।

## आइडेम्पोटेंट स्नैपशॉट बनाएँ

```bash
stackkit backup run --operation-id before-upgrade-2026-08-11 --json
```

लौटाए गए कंटेंट-एड्रेस्ड स्नैपशॉट एंकर को अपने सत्यापन प्रमाण के साथ रखें। वही ऑपरेशन ID दोबारा इस्तेमाल करने पर अनजाने में डुप्लिकेट बनाने के बजाय मौजूदा ऑपरेशन लौटता है।

## आइसोलेटेड स्टेजिंग में रीस्टोर करें

```bash
stackkit backup restore sha256:<snapshot-anchor-id> \
  --owner-approve \
  --operation-id restore-check-2026-08-11 \
  --json
```

यह स्नैपशॉट को सत्यापित करके CUE-स्वामित्व वाली स्टेजिंग में निकालता है। यह लाइव डेटा को नहीं बदलता। आगे बढ़ने से पहले लौटाए गए रीस्टोर-रिज़ल्ट ID की समीक्षा करें।

## सत्यापित रीस्टोर को सक्रिय करें

```bash
stackkit backup restore activate sha256:<restore-result-id> \
  --owner-approve \
  --operation-id restore-activation-2026-08-11 \
  --json
```

एक्टिवेशन ज़रूरी सेफ़्टी स्नैपशॉट बनाता है, प्लान के स्वामित्व वाले वॉल्यूम सेट को ठीक-ठीक बदलता है, रनटाइम को रीस्टार्ट करता है और ओनर बाइंडिंग तथा सेवाओं को सत्यापित करता है।

यदि एक्टिवेशन बीच में रुक जाए, तो उसी ऑपरेशन को स्पष्ट रूप से रिकवर करें:

```bash
stackkit backup restore recover restore-activation-2026-08-11 \
  --owner-approve \
  --rollback \
  --json
```

<Warning>
  सफल बैकअप रिकवरी का प्रमाण नहीं है। अपूरणीय फ़ाइलों के लिए स्टैक पर भरोसा करने से पहले गैर-महत्वपूर्ण डेटा के साथ स्टेज्ड रीस्टोर का अभ्यास करें।
</Warning>
