CLI आपको अलग-अलग कमांड से गुज़ारती है: अपने चुनाव सहेजें, उन्हें जाँचें,
डिप्लॉयमेंट की समीक्षा करें, उसे लागू करें, और देखें कि अब भी किस पर ध्यान चाहिए। हर
कमांड की अपनी हेल्प है। यह अपने-आप पूरी डिप्लॉयमेंट से आगे नहीं बढ़ती
और न ही आपके लिए Kit चुनती है।

यह वॉकथ्रू नेटिव CLI का वर्णन करता है, जैसी वह
[वर्तमान सार्वजनिक रिलीज़](https://github.com/kombifyio/StackKits/releases/latest) में शिप होती है।
Standard Mode बिना kombify खाते या Techstack के काम करता है। स्थानीय ओनर कुंजियाँ
और डिप्लॉयमेंट प्रमाण आपके वर्कस्पेस में रहते हैं।

## अपना शुरुआती बिंदु चुनें

| एंट्री | क्या होता है | आगे कहाँ जाएँ |
| --- | --- | --- |
| [टूलचेन इंस्टॉलर](/hi/guides/stackkits/choosing-a-kit#install-only-the-toolchain) | CLI और कैटलॉग इंस्टॉल करता है; सेवाओं को आप अलग से कॉन्फ़िगर और लागू करते हैं। | नीचे चरण 1। |
| [Basement क्विकस्टार्ट](/hi/stackkits/quickstart) | समर्थित Ubuntu सर्वर पर पूर्वापेक्षाएँ इंस्टॉल करता है, वर्कस्पेस और स्थानीय ओनर को इनिशियलाइज़ करता है, और डिफ़ॉल्ट Basement सेवाएँ लागू करता है। | नीचे चरण 5, `~/my-homelab` में। |

Basement बूटस्ट्रैप केवल उसी होस्ट पर चलाएँ जिसे आप कॉन्फ़िगर करना चाहते हैं। सेवाएँ इंस्टॉल किए बिना
CLI पर पहली नज़र के लिए टूलचेन पथ चुनें।
Windows उपयोगकर्ता सार्वजनिक रिलीज़ ZIP से CLI ले सकते हैं; इससे Windows
समर्थित नेटिव Basement रनटाइम लक्ष्य नहीं बन जाता। इंस्टॉलेशन लक्ष्य के लिए
[OS संगतता संदर्भ](/hi/stackkits/reference/os-compatibility) देखें।

## 1. CLI जाँचें और वर्कस्पेस बनाएँ

टूलचेन इंस्टॉल करने के बाद टर्मिनल खोलें:

```bash
stackkit version
stackkit --help
mkdir my-homelab
cd my-homelab
```

हेल्प कमांड को सेटअप, चालू देखभाल और संदर्भ में समूहित करती है;
[CLI संदर्भ](/hi/stackkits/reference/cli/overview) हर कमांड को उसके
फ़्लैग और उदाहरणों के साथ सूचीबद्ध करता है। इस वॉकथ्रू में एक ही डिप्लॉयमेंट डायरेक्टरी रखें। प्रयोग के लिए
नई डायरेक्टरी उपयोग करें, मौजूदा कॉन्फ़िगरेशन को बदलें नहीं।

## 2. अपने चुनाव सहेजें

कैटलॉग डिफ़ॉल्ट के साथ Basement Kit के लिए:

```bash
stackkit init basement-kit --catalog-defaults --owner-source=local
```

`init` `stack-spec.yaml` और स्थानीय ओनर कस्टडी बनाता है। यह सहेजे गए
कॉन्फ़िगरेशन का पथ और अगले `validate` तथा `generate` कमांड प्रिंट करता है। इसने
सेवाएँ इंस्टॉल नहीं की हैं।

कैटलॉग डिफ़ॉल्ट स्पष्ट चुनावों के रूप में दर्ज होते हैं। चुने गए Kit को ज़रूरत होने पर आवश्यक इनपुट माँगा
जाता है। नए वर्कस्पेस में Kit का फ़ोटो वर्कलोड शामिल करने के लिए पिछले init कमांड के **बजाय**
यह उपयोग करें:

```bash
stackkit init basement-kit --catalog-defaults --owner-source=local --use-case photos
```

इस बिंदु पर फ़ोटो वर्कलोड एक चयन है, चलती हुई फ़ोटो लाइब्रेरी नहीं।
सहेजी गई फ़ाइल में स्टोरेज पथ, डोमेन, चुने गए एप्लिकेशन और नोड सेटिंग की समीक्षा करें। देखें [StackSpec कॉन्फ़िगर करें](/hi/guides/stackkits/configure-stack-spec)।

स्क्रिप्ट के लिए `init` में `--non-interactive` जोड़ें। तब ज़रूरी इनपुट छूटने पर
पूछने के बजाय विफल हो जाता है। यह फ़्लैग बाद की डिप्लॉयमेंट क्रियाओं को स्वीकृत नहीं करता।
`stackkit init --help` उपलब्ध विकल्प बताता है; जिन फ़्लैग को
लीगेसी संगतता के रूप में चिह्नित किया गया है, वे इस नेटिव वॉकथ्रू के दायरे से बाहर हैं।

## 3. सत्यापित करें, जनरेट करें और समीक्षा करें

```bash
stackkit validate
stackkit generate
stackkit plan --json
```

सत्यापन कॉन्फ़िगरेशन को Kit अनुबंध के विरुद्ध जाँचता है। जनरेशन डिप्लॉयमेंट आर्टिफ़ैक्ट और
प्रमाण लिखता है। प्लान आपको होस्ट बदलने से पहले चुने गए
वर्कलोड, पथ और तैयारी की जाँच करने देता है।

`readiness.generation.status` और `readiness.apply.status` देखें, और
किसी भी ब्लॉकर को पढ़ें। ज़रूरत हो तो कॉन्फ़िगरेशन सुधारें और फिर से जनरेट करें। तैयार
प्लान का मतलब यह नहीं कि एप्लिकेशन पहले से चल रहे हैं।

## 4. लक्ष्य जाँचें और लागू करें

समर्थित लक्ष्य होस्ट पर, उसी वर्कस्पेस के साथ:

```bash
stackkit prepare
stackkit apply
```

नेटिव CLI पथ पर `prepare` Docker, Compose, स्टोरेज और पोर्ट जैसी होस्ट पूर्वापेक्षाएँ जाँचता है।
यह छूटे हुए होस्ट पैकेज इंस्टॉल नहीं करता। लागू करने से पहले बताई गई पूर्वापेक्षाएँ हल करें।

`apply` होस्ट को बदलता है। इसके अनुमोदन प्रॉम्प्ट और इच्छित बदलावों की समीक्षा करें।
विस्तृत लाइफ़साइकल जाँच के लिए
[समीक्षा करें, लागू करें और सत्यापित करें](/hi/guides/stackkits/review-plan-and-apply) देखें।
यदि आपने Basement बूटस्ट्रैप उपयोग किया है, तो शुरुआती apply हो चुका है;
सिर्फ़ टूर पूरा करने के लिए उसे दोहराएँ नहीं।

## 5. पता करें कि क्या उपयोग योग्य है

```bash
stackkit verify --http --json
```

`verify` स्टैक स्पेक, डिप्लॉयमेंट स्टेट, Docker डेमन, StackKit
कंटेनर और उनकी हेल्थ जाँचता है, और `--http` के साथ जनरेट किए गए एक्सेस सारांश के रूट भी जाँचता है।
हर विफल जाँच अपना कारण साथ लाती है। केवल कॉन्फ़िगर किया गया पता यह सिद्ध नहीं करता कि कोई एप्लिकेशन पहुँच में है; सफल HTTP
जाँच करती है।

जब किसी खाते को अब भी कॉन्फ़िगर करना हो, तो एप्लिकेशन की सेटअप गाइड का पालन करें।
समर्थित सेटअप क्रियाओं के लिए `stackkit setup --help` उपयोग करें। अंत में
एप्लिकेशन खोलें और कोई छोटा वास्तविक काम करें, जैसे अपनी फ़ोटो लाइब्रेरी में एक टेस्ट फ़ोटो
जोड़ना। केवल CLI इंस्टॉलेशन की सफलता यह सिद्ध नहीं करती कि
यह काम चलता है।

## 6. फिर शुरू करें और समस्याएँ सुलझाएँ

उसी डिप्लॉयमेंट डायरेक्टरी में लौटें:

```bash
stackkit verify --json
stackkit drift detect --json
stackkit logs list --json
stackkit logs get <run-id> --json
```

`drift detect` कुछ बदले बिना लाइव Compose रनटाइम को हल किए गए प्लान,
जनरेट किए गए आर्टिफ़ैक्ट और हस्ताक्षरित apply प्रमाण के विरुद्ध जाँचता है,
और `logs get` `logs list` से मिले किसी एक रन का संरचित लॉग पढ़ता है। जारी रखने के लिए
बताए गए कारण और अगली कार्रवाई का उपयोग करें। ऑपरेशन विफल होने पर वर्कस्पेस को सुरक्षित रखें;
`init` से दोबारा शुरू न करें और किसी ब्लॉकर को बायपास करने के लिए जनरेट की गई फ़ाइलें संपादित न करें। ओनर कुंजियाँ और एक्सेस रिकॉर्ड निजी रखें, और
डायग्नोस्टिक आउटपुट साझा करने से पहले उसकी समीक्षा करें।

चालू देखभाल के लिए [Day-2 ऑपरेशन](/hi/stackkits/reference/day-2-operations)
और [बैकअप और रीस्टोर](/hi/guides/stackkits/back-up-and-restore) उपयोग करें। Kit चयन
और Techstack में निर्देशित कॉन्फ़िगरेशन अनुभव एक वैकल्पिक
अगला कदम हैं; इस स्थानीय CLI वर्कफ़्लो के लिए वे आवश्यक नहीं हैं।
