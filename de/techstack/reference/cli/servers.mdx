## techstack api servers detach

Genau einen vom Kunden betriebenen BYO-Server widerrufen und abkoppeln.

Behält den terminalen kanonischen Server-Beleg und führt keinen Aufruf der Anbieter-API aus.

## techstack api servers maintenance run

Für einen eigenen Server einen OS-Update-Plan, ein OS-Update oder einen Neustart einreihen.

Erfordert das Edge-signierte Entitlement `techstack.servers.maintenance`, die Ownership des Servers im Tenant und für delegierte native MCP-Aufrufe eine aktuelle, an den Server gebundene dauerhafte Autorisierung. Diese drei gewöhnlichen Aktionen erfordern weder eine frische MFA noch eine separate owner_approved-Bestätigung. Der Body wird strikt dekodiert: exakte Schlüssel in Kleinbuchstaben, keine Duplikate, keine unbekannten Felder. Eine Wiederholung mit demselben Idempotency-Key gibt den gespeicherten Beleg vor der Zielvalidierung zurück. Pro Server darf ein Neustart oder OS-Update und getrennt davon ein Update-Plan aktiv sein; ein Job, der bis zu seiner Frist nicht fertig ist, schlägt mit `deadline_exceeded` fehl und gibt seinen Slot frei. Die Aktion wird in `allowed_actions` nur angeboten, wenn der Server-Agent `stackkit.host-maintenance.v1` ankündigt, und `reboot` nur, wenn der Server außerdem `host_boot_id` meldet. Ablehnungen sind client-error-envelope/v1-Dokumente; der 409-`reason_code` ist einer von control_plane_host, substrate_node, protected_demo_server, service_locked, maintenance_active, node_operation_active, plan_stale, agent_capability_missing, boot_id_unknown, agent_not_connected, heartbeat_stale, inventory_revision_stale oder idempotency_key_reused; 403 trägt entitlement_required oder maintenance_origin_authority_denied.

```bash
techstack api servers maintenance run <server-id> [flags]
```

## techstack api servers network rebind

Einen versetzten Server an sein aktuelles Netzwerk neu binden.

Führt `stackkit network rebind` über kombify Guard auf dem Server aus: Der Node erkennt seine LAN-Adresse erneut, stellt den signierten LAN-DNS-Verwahrungseintrag erneut aus und generiert und wendet den Workspace erneut an. Die Anfrage hat keinen Body. Erforderlich sind der Owner, die Inventory-Berechtigung operate, das Entitlement `techstack.servers.maintenance` und ein verbundener Guard (andernfalls 409 `server_network_not_ready`). Ist bereits eine erneute Bindung eingereiht oder aktiv, wird deren Job zurückgegeben, statt einen weiteren einzureihen.

```bash
techstack api servers network rebind <server-id> [flags]
```

<Warning>Erfordert Bestätigung: Diese Operation erkennt die aktuelle Netzwerkadresse des Servers erneut, stellt seinen signierten lokalen DNS-Eintrag erneut aus und wendet seinen Workspace erneut an. Übergib `--yes` oder beantworte die Rückfrage; ein nicht interaktiver Lauf ohne `--yes` stoppt vor jeder Anfrage mit Exit-Code 9.</Warning>

## techstack api servers reach set

Den Server unter einer kombify.me-Adresse veröffentlichen oder die Veröffentlichung beenden.

Standardmäßig wird nichts veröffentlicht: Ein gekoppelter Server hat keine öffentliche Route und das Relay überträgt keinen Verkehr. Der Owner aktiviert dies pro Server mit einem ausdrücklichen `service`-Namen und `target_port` (der Ursprung ist immer die Loopback-Adresse des Guard-Hosts, niemals eine andere Maschine) und kann es jederzeit zurücknehmen. Das Relay authentifiziert den Guard, nicht den Besucher; der Dienst auf diesem Port muss sich deshalb selbst schützen. Die Aktivierung erfordert den Owner, das Entitlement `techstack.servers.maintenance` und eine frische Multi-Faktor-Anmeldung (Grund `server_reach_step_up_required`); die Rücknahme wird niemals dadurch blockiert. Die Antwort enthält den reach-Abschnitt des Server-Lesemodells; der Reconciler erstellt oder entfernt anschließend die Route.

```bash
techstack api servers reach set <server-id> [flags]
```

<Warning>Erfordert Bestätigung: Diese Operation veröffentlicht einen Dienst des Servers unter einer öffentlichen kombify.me-Adresse, die jeder im Internet öffnen kann. Übergib `--yes` oder beantworte die Rückfrage; ein nicht interaktiver Lauf ohne `--yes` stoppt vor jeder Anfrage mit Exit-Code 9.</Warning>

## techstack api servers security auto-repair set

Standardmäßig deaktiviert. ## techstack api servers security repairs request

Benannte abweichende Host-Sicherheitskontrollelemente reparieren.

Fordert eine begrenzte Reparatur von Kontrollelementen an, die frische Host-Sicherheitsnachweise als abweichend und automatisch reparierbar ausweisen. Erforderlich sind der Server-Owner, das Edge-signierte Entitlement `techstack.servers.maintenance` und eine frische Multi-Faktor-Anmeldung (höchstens 300 Sekunden alt). Die Reparatur wird als typisierter, journalisierter Guard-Befehl übertragen, der `stackkit host security repair --apply` für genau die benannten Kontrollelemente ausführt. StackKits lehnt vor jeder Änderung eine Änderung ab, die den Verwaltungsweg unterbrechen oder den Owner aussperren würde. Grenzen: jeweils eine Reparatur pro Server (409 `repair_in_progress`), eine Wartezeit pro Kontrollelement (429 `repair_cooldown`), ein tägliches Versuchslimit pro Kontrollelement (429 `repair_attempts_exhausted`) und eine Sicherung nach aufeinanderfolgenden Fehlern (429 `repair_circuit_open`); die 429-Antworten enthalten `retry_after`. Ein konformes Kontrollelement (409 `control_not_drifted`), eines mit genehmigter Ausnahme (`control_has_exception`), ein manuelles (`control_not_repairable`), eines ohne erforderlichen autorisierten SSH-Schlüssel (`needs_authorized_key`) oder ein nicht beobachtetes wird abgelehnt. Der Body wird strikt dekodiert.

```bash
techstack api servers security repairs request <server-id> [flags]
```

<Warning>Erfordert Bestätigung: Diese Operation stellt die benannten Host-Sicherheitskontrollelemente (Firewall, SSH, Brute-Force-Schutz, automatische Updates) über kombify Guard auf dem Server wieder her. Übergib `--yes` oder beantworte die Rückfrage; ein nicht interaktiver Lauf ohne `--yes` stoppt vor jeder Anfrage mit Exit-Code 9.</Warning>

## techstack api servers security verify

kombify Guard um eine frische Beobachtung der Host-Sicherheit bitten.

Hält fest, dass eine frische Beobachtung der Host-Baseline angefordert ist. Der Guard antwortet beim nächsten Check-in (innerhalb etwa einer Minute) mit einem neuen Bericht; auf dem Host wird nichts verändert. Das `security`-Lesemodell des Servers wird ausschließlich durch diesen Bericht aktualisiert, nie durch diese Anfrage. Ein Server eines anderen Tenants oder Owners liefert 404; ein Server ohne Guard liefert 409 `guard_not_connected`.
