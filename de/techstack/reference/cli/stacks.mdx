## techstack api stacks create

Ein StackKit-Deployment im Homelab des Owners erstellen.

Erstellt ein internes StackKit-Deployment unter dem Singleton-Homelab des authentifizierten B2C-Owners aus dem kanonischen StackKits-stack-spec-Payload, der als `stack_spec` übergeben wird. Die Legacy-Route `/stacks` und das Antwortfeld `stack_id` bezeichnen dieses Deployment; sie erstellen oder wählen kein zweites Homelab-Produkt. Eine TechStack-Instanz kann viele Owner bedienen, jeder mit seinem eigenen Homelab. Legacy-Payloads im Stil `user_config`/kombination werden an dieser Kompatibilitätsgrenze weiterhin akzeptiert. Wizard-Clients sollten einen stabilen `X-Idempotency-Key` senden; Wiederholungen mit demselben Key und Payload geben das ursprüngliche Deployment, den geplanten Server und den Bereitstellungs-Job zurück.

```bash
techstack api stacks create [flags]
```

<Warning>Erfordert Bestätigung: Diese Operation erstellt das StackKit-Deployment und startet die Bereitstellung, die abgerechnete Server bestellen kann. Übergib `--yes` oder beantworte die Rückfrage; ein nicht interaktiver Lauf ohne `--yes` stoppt vor jeder Anfrage mit Exit-Code 9.</Warning>

## techstack api stacks managed-runtimes add

Einen verwalteten Node über native Provider Control hinzufügen.

Erstellt oder setzt genau einen deterministischen Add-Server-Job für das exakte eigene StackKit-Deployment fort. Der Standard-`Idempotency-Key` ist Pflicht. Eine Wiederholung mit demselben Key und derselben kanonischen Anfrage gibt die ursprünglichen Korrelationen von Job, Lease, Runtime-Server, Ressourcengeneration und Anbieter-Operation zurück; die Wiederverwendung mit abweichendem Intent schlägt mit 409 fehl.

Der rohe Key wird nie gespeichert oder zurückgegeben. Eine verlorene Antwort oder ein unsicheres Ergebnis der nativen Zulassung bleibt nur mit demselben Key fortsetzbar. Eine HTTP-Annahme bedeutet, dass die native Zulassung dauerhaft gespeichert ist und die Reconciliation beim Anbieter aussteht; sie behauptet nie, dass die VM bereits bereitgestellt oder gesund ist. Eine neue Zulassung reserviert den Kapazitäts-Slot des authentifizierten Tenants/Owners atomar zusammen mit der Lease-Generation und der Anbieter-Operation. Stellt die maßgebliche native Zulassung fest, dass diese begrenzte Kapazität voll ist, speichert sie ein nicht wiederholbares 403-Ergebnis, und eine Wiederholung dieses abgelehnten Jobs gibt dasselbe Ergebnis zurück. Exakte Wiederholungen einer bereits festgeschriebenen Zulassung verwenden deren bestehende Reservierung weiter. Diese Version gibt Reservierungen nicht automatisch frei: Ein terminaler oder lokaler Stilllegungszustand allein gibt keinen Slot frei. Lease-Inventory und Feature-Delivery-Flags autorisieren oder verweigern nie Kapazität. Eine gehostete neue Zulassung erfordert außerdem die v2-signierten kommerziellen Runtime- und Anbieter-Entitlements sowie die signierte Modus-/Limit-Entscheidung `cloud.runtime.credits` `managed_servers`; Feature-Flags allein gewähren nie Anbieter-Kapazität. Self-Host-OSS verwendet statt einer SaaS-Entitlement-Abhängigkeit seine bei der Konstruktion festgelegte statische Release-Manifest-Richtlinie.

```bash
techstack api stacks managed-runtimes add <stack-id> [flags]
```

## techstack api stacks resume-enrollment

Eine überfällige Wartephase eines verwalteten Node auf seiner exakten bestehenden VM fortsetzen.

Authentifizierte, idempotente Wiederherstellung für einen gespeicherten `waiting_enrollment`-, `waiting_provider_provision`- oder `waiting_canonical_guard`-Job, dessen `next_resume_at` über die begrenzte Kulanzzeit hinaus überfällig ist. Der Server validiert das eigene StackKit-Deployment, den Quell-Job, den Wartegrund, die exakte Lease, die aktive Foundation-Rolle und den kanonischen Node als eine Operation. Er beendet die exakte Quell-Wartephase atomar, erstellt oder rehydriert genau ein deterministisches Ersatz-Deploy, das an dieselbe Lease und denselben Node gebunden ist, und wiederholt diesen Job bei späteren Aufrufen. Vor dem Eintritt in den Handler erwerben Queue-Worker atomar den dauerhaften `tenant/stack`-Kompatibilitäts-Ausführungsanspruch; dadurch werden verschiedene Jobs für dasselbe StackKit-Deployment über Techstack-Replikas hinweg serialisiert. Der Anspruch bleibt dauerhaft `running`, bis der Handler endet, auch während eines Abbruchs. Dieser Endpoint löst nie die Erstellung einer VM beim Anbieter aus und wählt nie eine neuere VM. Ein Ersatz, der nach einem Absturz als dauerhaft `running` vorgefunden wird, bricht sicher ab, wird als derselbe Job gemeldet und nie automatisch dupliziert; die Reconciliation von Runtime-Aktionen bleibt eine separate Aufgabe des Operators.

```bash
techstack api stacks resume-enrollment <stack-id> [flags]
```

| | |
| --- | --- |
| HTTP | `POST /api/v1/stacks/{id}/resume-enrollment` |

| `<stack-id>` | string | **Erforderlich.** Stack-ID. |
| `--job-id` | string | **Erforderlich.** Gespeicherter Quell-Job, der aktuell als waiting_enrollment projiziert wird. |

## techstack api stacks retry-rollout

Der deterministische, dauerhafte Ersatz umgeht die Erstellung einer VM beim Anbieter, gewinnt vor dem Eintritt in den Handler einen dauerhaften `tenant/stack`-Kompatibilitäts-Ausführungsanspruch und wird bei wiederholten Aufrufen dieser Operation wiederholt. ## techstack api stacks routing ensure

Das gewünschte Routing-Overlay für genau ein StackKit-Deployment und einen Node sicherstellen.

Speichert atomar ein idempotentes, revisioniertes Routing-Overlay, ohne den unveränderlichen Intent des Benutzers zu ändern. server_id ist immer exakt und Pflicht. lease_id ist für verwaltete Runtimes Pflicht und entfällt für eine lokale/Basement-Runtime, die keine Lease hat. Bei einem verwalteten Ziel startet eine Anfrage mit ensure_rollout=true die bestehende Deploy-Pipeline erst, nachdem nachgewiesen ist, dass ihre gewählte aktive Foundation-Lease und ihr kanonischer Node genau diesem Ziel entsprechen. Die API meldet den resultierenden Job nie als bereits angewendet. Das Overlay wird nur beim Ableiten der StackKits-Artefakte verwendet, und dieser Pfad erstellt oder wählt nie eine Ersatz-VM.

techstack api stacks routing ensure <stack-id> [flags]
