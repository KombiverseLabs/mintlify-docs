StackKits turns declarative infrastructure contracts into deployable homelab environments. This page explains the end-to-end flow from your intent to running services.

## The deployment pipeline

Every StackKits deployment follows the same lifecycle, regardless of whether you use the one-line installer, the CLI, or an AI agent:

```
Intent → Spec → Validate → Generate → Plan → Apply → Verify
```

<Steps>
  <Step title="Intent collection">
    You express what you want: which kit, which domain, which services.
    This happens through the CLI wizard (`stackkit init`), a `stack-spec.yaml` file, or an API request.
  </Step>

  <Step title="Spec creation">
    Your intent becomes a `stack-spec.yaml` — the editable deployment contract.
    This is the single file you own and customize. Everything downstream is generated.
  </Step>

  <Step title="CUE validation">
    The spec is validated against CUE schema contracts that define allowed structures,
    type constraints, and service dependencies. Invalid specs are rejected before
    any infrastructure is touched.
  </Step>

  <Step title="Artifact generation">
    CUE contracts + Go resolver bind your spec into concrete deployment artifacts:
    OpenTofu configurations, Docker Compose files, and platform metadata under `deploy/`.
  </Step>

  <Step title="Plan preview">
    `stackkit plan` shows exactly what will be created, modified, or removed — a
    dry-run preview before any mutation happens.
  </Step>

  <Step title="Apply">
    OpenTofu provisions the infrastructure. The selected PaaS (Coolify, Dokploy, Komodo)
    bootstraps. System services start. Service URLs are printed.
  </Step>

  <Step title="Verify">
    Read-only post-deployment checks confirm that all expected services are running,
    reachable, and healthy. Evidence is preserved for audit.
  </Step>
</Steps>

## Architecture layers

Every StackKit resolves through three layers, each building on the one below:

<Tabs>
  <Tab title="Foundation">
    The base layer that every deployment needs:

    - **Host bootstrap** — Docker installation, system packages
    - **Security baseline** — Firewall rules, SSH hardening
    - **Owner/break-glass** — Recovery credentials, admin bootstrap
    - **Secrets management** — Secure credential generation and storage
    - **Base network** — Docker networks, DNS resolution
    - **Telemetry** — Minimal health monitoring
  </Tab>

  <Tab title="Platform">
    The infrastructure services that make your homelab work:

    - **PaaS adapter** — Coolify, Dokploy, or Komodo integration
    - **Reverse proxy** — Traefik for routing and TLS termination
    - **Identity provider** — PocketID for user authentication
    - **Login gateway** — TinyAuth for service protection
    - **Service registration** — Automatic DNS and routing setup
    - **Logging and health** — Centralized logs and uptime monitoring
  </Tab>

  <Tab title="Application">
    The user-facing services that provide actual functionality:

    - **Photos** — Immich (Google Photos alternative)
    - **Password vault** — Vaultwarden (Bitwarden compatible)
    - **Media** — Jellyfin (media streaming)
    - **Dashboard** — Homepage (service overview)
    - **Monitoring** — Uptime Kuma, Netdata, Beszel, Dozzle
    - **Development** — PaaS tools for your own apps
  </Tab>
</Tabs>

## Key components

| Component | Role |
|-----------|------|
| **stackkit CLI** | Operator workflow: init, prepare, validate, generate, plan, apply, verify |
| **stackkit-server** | HTTP API for catalog, validation, generation preview, and management |
| **CUE contracts** | Schema definitions, defaults, constraints — the technical source of truth |
| **OpenTofu** | Infrastructure-as-code engine (packaged with StackKits) |
| **PaaS adapter** | Integrates with Coolify/Dokploy/Komodo for container orchestration |

## Data ownership

Understanding what you own vs. what StackKits generates:

| Artifact | Owner | Editable? |
|----------|-------|-----------|
| `stack-spec.yaml` | You | Yes — this is your deployment contract |
| CUE contracts | StackKits | No — updated via kit upgrades |
| `deploy/` directory | Generated | No — regenerated on every `stackkit generate` |
| OpenTofu state | Generated | No — managed by OpenTofu |
| `.stackkit/state.yaml` | StackKits | No — internal deployment state |
| Service data volumes | You | Yes — your actual data (photos, passwords, etc.) |

<Warning>
  Never hand-edit files in the `deploy/` directory. They are regenerated from your spec and CUE contracts. Changes will be overwritten.
</Warning>

## Routing

StackKit does not add its own router when the selected PaaS already includes one. For Coolify, generated routes are served by Coolify's Traefik. For Komodo, StackKit provides one dedicated Traefik instance.

Your services are accessible at `<service>.<domain>`:
- `base.home.localhost` — Node Hub dashboard
- `auth.home.localhost` — PocketID identity
- `photos.home.localhost` — Immich
- `vault.home.localhost` — Vaultwarden

## First-run security

After deployment, the Node Hub is intentionally open until you complete owner setup:

1. Open the Node Hub at `base.<domain>`
2. Complete the PocketID owner registration (passkey-based)
3. Click **Protect Base Hub** — this enables TinyAuth protection
4. Technical bootstrap credentials are revealed once, then sealed

After protection, all services require authentication through PocketID or TinyAuth.

## What happens during an upgrade

See the [upgrade guide](/stackkits/guides/upgrading) for the full process. In short:

1. `stackkit kit upgrade` checks for new kit versions via the compatibility resolver
2. An atomic snapshot (Kopia backup + OpenTofu state copy) is created
3. New CUE contracts are applied, artifacts regenerated
4. OpenTofu applies the changes
5. If anything fails, `stackkit kit upgrade rollback` restores from the snapshot
