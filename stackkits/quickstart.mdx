This quickstart follows the current public StackKits release. The [StackKits website](https://stackkit.cc/getting-started) helps you choose an installation path, while the CLI remains the local execution authority.

## Bootstrap a Basement Kit

On a supported Ubuntu server, the Basement installer creates `~/my-homelab`,
installs the released artifacts and required runtime, initializes local owner
custody, bootstraps the local Admin/PocketID access, validates the generated
StackSpec, and applies the default Basement services:

```bash
curl -sSL https://base.stackkit.cc | sh
cd ~/my-homelab
stackkit version
stackkit logs latest --json
cat .stackkit/access.json
```

<Warning>
  A hosted kombify account is not required. StackKits itself still requires a
  local Owner/Admin, which this bootstrap creates automatically. Keep the
  generated access details private.
</Warning>

Prefer to install only the toolchain and full public catalog?

```bash
curl -sSL https://install.stackkit.cc | sh
```

To install only one kit's definitions alongside the CLI, pass its name to the toolchain installer:

```bash
curl -sSL https://install.stackkit.cc | sh -s -- basement-kit
```

You can pass `cloud-kit` or `modern-homelab` the same way.

<Note>
  The retired `base-kit` name is rejected. Update scripts that still pass it to
  use `basement-kit`.
</Note>

The shell installers resolve the current public release and support Linux and macOS on `amd64` and `arm64`. Windows users can download the `windows_amd64` ZIP from the [latest release](https://github.com/kombifyio/StackKits/releases/latest). See the [CLI walkthrough](https://stackkit.cc/getting-started/cli) for the website-guided path.

## Review or change the generated intent

Inspect `stack-spec.yaml` before generating output. In particular, review the absolute storage roots, the `home.test` local domain, site and node identities, and the empty optional workload selection.

If you used the toolchain-only installer, create the workspace yourself:

```bash
mkdir my-homelab
cd my-homelab

stackkit init basement-kit --owner-source=local
stackkit validate
```

On constrained hardware, declare the tier and device class at init:

```bash
stackkit init basement-kit --owner-source=local --compute-tier low --hardware-profile pi
```

`--compute-tier` writes `install.computeTier` (`low` | `standard` | `high`, default `standard`) and selects a module graph the kit declares. Basement Kit publishes all three tiers; Cloud Kit and Modern Home Lab publish only `standard` and `high`, so `--compute-tier low` on those kits fails closed at init and compile. `--hardware-profile` writes `nodes[0].hardware.profile`. The `pi` profile means a constrained homelab device class such as an SBC or low-RAM mini-PC, not a Raspberry Pi specifically, and it does not imply `computeTier: low`. See [Compute tiers](/stackkits/kits/basement-kit#compute-tiers) for what each Basement graph includes.

The StackSpec is the configuration input. CUE remains the validation authority and generated rollout files are outputs, not files to edit by hand. See [Configure a StackSpec](/guides/stackkits/configure-stack-spec) for current examples.

## Generate and inspect a changed plan

```bash
stackkit generate
stackkit plan --json
```

Confirm that generation and apply readiness are both `ready`, then review the selected workloads and artifact paths.

On a multi-node StackSpec, pass `--local-site` and `--local-node` to `stackkit generate` to name the node whose local inventory is attested. This is the same binding Apply uses. A multi-node generate without a bound local node fails closed instead of probing nothing.

## Runtime capacity admission

Apply attests the local CPU, RAM, and disk inventory before it resolves the plan. Core runtimes declare minimum capacity floors, and the compiler admits the selected compute tier graph against the attested facts before any side effects:

- A missing inventory fact blocks Apply with `inventory-fact-unverified`.
- An attested undersized host blocks Apply with `runtime-capacity-unsatisfied`.

Generation can still succeed while Apply is blocked. Fix the host or select a smaller tier, then generate and apply again. A failed Product Apply ends with retry, `stackkit status --json`, and `stackkit logs latest --json` guidance, plus the Run-ID when a local rollout run exists.

## Apply an intentional change

```bash
stackkit apply
stackkit logs latest --json
cat .stackkit/access.json
```

The Basement one-liner already performs the initial apply. Run these lifecycle
commands only after you intentionally change `stack-spec.yaml`. Keep the local
logs and access record with the workspace.

Re-running the Basement or Cloud installer on a workspace that already carries
deployment intent skips initialization and resumes `stackkit apply` from the
apply journal instead of failing. Use a different workspace directory for a
second deployment.

<Warning>
  StackKits does not provision a server or obtain provider credentials. For a Cloud Kit, prepare the host, domain, and DNS ownership yourself before applying a stack.
</Warning>

<Accordion title="Bootstrap a Cloud Kit workspace">
  The released Cloud installer requires a domain you control and, like the Basement installer, stops after initialization and validation:

  ```bash
  curl -sSL https://cloud.stackkit.cc | DOMAIN=example.com sh
  cd ~/my-cloud-homelab
  stackkit generate
  stackkit plan --json
  ```

  Public Cloud runtime evidence remains explicit per release, so treat this as a configuration bootstrap unless the current release notes include matching live evidence.
</Accordion>
