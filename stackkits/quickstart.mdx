This quickstart uses the released StackKits `v0.16.0` lifecycle. The [StackKits website](https://stackkit.cc/getting-started) helps you choose an installation path, while the CLI remains the local execution authority.

## Bootstrap a Basement Kit

On Linux or macOS, the Basement installer creates `~/my-homelab`, installs the released artifacts, initializes local owner custody, and validates the generated StackSpec:

```bash
curl -sSL https://base.stackkit.cc | STACKKIT_RELEASE_VERSION=0.16.0 sh
cd ~/my-homelab
stackkit version
stackkit validate
```

<Warning>
  The one-liner does not install Docker, prepare a host, run `generate`, or run `apply`. It bootstraps and validates the workspace; changing the host remains an explicit local decision.
</Warning>

Prefer to install only the toolchain and full public catalog?

```bash
curl -sSL https://install.stackkit.cc | STACKKIT_RELEASE_VERSION=0.16.0 sh
```

The shell installers support Linux and macOS on `amd64` and `arm64`. Windows users can download the `windows_amd64` ZIP from the [v0.16.0 release](https://github.com/kombifyio/StackKits/releases/tag/v0.16.0). See the [CLI walkthrough](https://stackkit.cc/getting-started/cli) for the website-guided path.

## Review the generated intent

Inspect `stack-spec.yaml` before generating output. In particular, review the absolute storage roots, the `home.test` local domain, site and node identities, and the empty optional workload selection.

If you used the toolchain-only installer, create the workspace yourself:

```bash
mkdir my-homelab
cd my-homelab

stackkit init basement-kit --owner-source=local
stackkit validate
```

The StackSpec is the configuration input. CUE remains the validation authority and generated rollout files are outputs, not files to edit by hand. See [Configure a StackSpec](/guides/stackkits/configure-stack-spec) for current examples.

## Generate and inspect the plan

```bash
stackkit generate
stackkit plan --json
```

Confirm that generation and apply readiness are both `ready`, then review the selected workloads and artifact paths.

## Apply explicitly and verify

```bash
stackkit apply
stackkit verify --http --json
stackkit status --json
```

Keep the verification output with the workspace. It is the record of what the local lifecycle observed after the apply.

<Warning>
  StackKits does not provision a server or obtain provider credentials. For a Cloud Kit, prepare the host, domain, and DNS ownership yourself before applying a stack.
</Warning>

<Accordion title="Bootstrap a Cloud Kit workspace">
  The released Cloud installer requires a domain you control and, like the Basement installer, stops after initialization and validation:

  ```bash
  curl -sSL https://cloud.stackkit.cc | STACKKIT_RELEASE_VERSION=0.16.0 DOMAIN=example.com sh
  cd ~/my-cloud-homelab
  stackkit generate
  stackkit plan --json
  ```

  Public v0.16.0 Cloud runtime evidence is still pending, so treat this as a configuration bootstrap rather than a production-readiness claim.
</Accordion>
