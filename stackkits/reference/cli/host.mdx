## stackkit host delivery

Manage this node's sealed host delivery recipient.

Sealed host delivery brings Wallet items, backup targets and SSH access to this node. A delivering authority seals each value to this node's recipient key (HPKE, pkg/hostdelivery); only this node opens it into its own custody. Techstack and Guard carry ciphertext and references only.

```bash
stackkit host delivery [flags]
```

Subcommands: [`stackkit host delivery detach`](#stackkit-host-delivery-detach), [`stackkit host delivery recipient`](#stackkit-host-delivery-recipient), [`stackkit host delivery status`](#stackkit-host-delivery-status)

### stackkit host delivery detach

Stop host delivery to this node and list the delivered secrets to rotate.

Detach this node from host delivery: every delivered secret is marked as needing rotation, retired recipient keys are destroyed, and no delivery opens until the node is re-enrolled with 'host delivery recipient `--rotate`'. The result lists the references and versions to rotate where they came from; it never contains a value. Values already in local custody stay usable here.

```bash
stackkit host delivery detach [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--owner-approve` | bool | — | Authorize detaching this node |

**Examples**

```bash
stackkit host delivery detach --owner-approve
```

### stackkit host delivery recipient

Prove this node's recipient key, pin the delivering authority, or rotate the key.

Print a statement, signed by the local Owner key, that binds this node's recipient key and its generation to this Site and node and echoes the caller's challenge. The private key never leaves local custody.

`--authority-key` pins the delivering authority's Ed25519 public key for the current generation; Wallet items and SSH access open only when signed by it. A pinned key is never replaced in place. `--rotate` re-enrolls the node under the next generation (and with `--authority-key` pins a new authority): the previous key still opens deliveries issued before the rotation for at most their 15-minute lifetime and is then destroyed. Rotation also ends a detach.

```bash
stackkit host delivery recipient [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--authority-key` | string | — | Delivering authority Ed25519 public key (base64) to pin for this generation |
| `--authority-key-id` | string | — | Key ID the delivering authority signs envelopes with |
| `--challenge` | string | — | Fresh value from the delivering authority that the statement must echo |
| `--owner-approve` | bool | — | Authorize this node's recipient change |
| `--rotate` | bool | — | Re-enroll under the next recipient generation |

**Examples**

```bash
stackkit host delivery recipient --challenge "$CHALLENGE" --authority-key "$WALLET_KEY" --authority-key-id wallet-1 --owner-approve
stackkit host delivery recipient --challenge "$CHALLENGE" --rotate --owner-approve
```

### stackkit host delivery status


## stackkit host reboot

Schedule a reboot of this node.

Schedule a reboot of this node after a short delay and return immediately.

The returned boot_id_before identifies the current boot, so a caller can tell the node came back by reading a different boot ID. The command refuses a node that runs the Techstack control plane, a node where apt or dpkg holds its lock or a host update runs, and a node that cannot boot unattended (volumes in /etc/crypttab that need a passphrase, or no apt).

When the delay ends a guard checks again, waits up to 15 minutes for any package operation to finish, and requests the reboot while holding the dpkg locks. A node that stays busy is not rebooted; its boot ID stays the same.

```bash
stackkit host reboot [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--delay` | duration | `30s` | Time until the reboot starts (1s to 5m) |
| `--json` | bool | — | Emit the stackkit.host-maintenance/v1 result as machine-readable JSON |
| `--yes` | bool | — | Confirm that this node may reboot |

**Examples**

```bash
# Reboot this node in 30 seconds
sudo stackkit host reboot --yes

# Reboot in two minutes and report the boot ID to compare against
sudo stackkit host reboot --yes --delay 2m --json
```

## stackkit host remediate

Show or carry out fixes for what host preflight found.

List the fixes that answer this host's preflight findings, or carry one out.

Without `--apply` nothing is changed: the command measures the host and prints what each fix would do, whether it can be undone, and whether it needs root.

With `--apply` &lt;id&gt; `--yes` the named fix runs, and the check that justified it is measured again afterwards so the result states what actually changed rather than that something was attempted.

```bash
stackkit host remediate [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--apply` | string | — | Carry out the named resolution (requires `--yes`) |
| `--auto-reversible` | bool | — | Carry out every undoable fix that may run unattended (requires `--yes`) |
| `--json` | bool | — | Emit the remediation plan or record as machine-readable JSON |
| `--policy` | string | — | Preflight policy used to find findings: strict or warn (default) |
| `--yes` | bool | — | Confirm that the named resolution may change this host |

**Examples**

```bash

stackkit host remediate

# Carry out one fix by the ID the list printed
stackkit host remediate --apply <resolution-id> --yes

# Carry out every undoable fix that may run unattended
stackkit host remediate --auto-reversible --yes
```

## stackkit host security

Verify and repair the host security baseline with versioned evidence.

Observe this node against the StackKits host security baseline, and restore what drifted without cutting the management path.

'verify' never changes the host. It produces stackkit.host-security-evidence/v1 for the firewall, sshd, brute-force protection, automatic and pending security updates, reboot state, kernel parameters, exposed listeners and certificate expiry, and for the SSH CA trust and host certificate delivered to this node ('host ssh apply') once they are recorded. Every control is compliant, drifted, unknown or an owner-approved exception, and the evidence expires: a stale observation is unknown, and an unknown control never counts as compliant.

It works on its own (Standard Mode, no account) and through the pinned CLI when Techstack manages the deployment (`--mode` advanced).

```bash
stackkit host security [flags]
```

Subcommands: [`stackkit host security repair`](#stackkit-host-security-repair), [`stackkit host security status`](#stackkit-host-security-status), [`stackkit host security verify`](#stackkit-host-security-verify)

### stackkit host security repair

Restore drifted baseline controls without cutting the management path.

Plan, or with `--apply` carry out, the restoration of drifted controls.

Without `--apply` nothing is changed: the command measures the host and prints what each repair would do. With `--apply` only the named (`--control`) or drifted controls are touched, and every change is checked first:

```text
  - the firewall always keeps admitting the ssh sessions in use and every
    --management-source on every sshd port, and a policy that would not is
    refused before it is loaded;
  - password logins are disabled only when an account holds an authorized key;
    without one they stay on, the step is refused with reason no_authorized_key
    and the rest of the baseline is still repaired. The previous sshd and
    firewall configuration is restored if the new one does not validate or does
    not take effect;
  - fail2ban never bans the management path.
```

A control that cannot be observed, or that the owner approved an exception for, is not touched. A Cloud site's firewall and root login are restored by 'stackkit apply'. Each step records the control before and after, and a repeated repair of a compliant control changes nothing.

```bash
stackkit host security repair [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--apply` | bool | — | Carry out the repair; without it the command only plans |
| `--control` | stringArray | — | Restrict the repair to this control ID (repeatable) |
| `--declared-port` | stringArray | — | Declared service port as tcp/443 or udp/5353 (repeatable) |
| `--exceptions` | string | `/etc/stackkit/host-security/exceptions.json` | Owner-controlled exceptions file (each exception needs an owner and an expiry) |
| `--freshness` | duration | `15m0s` | How long the evidence may be relied on before it expires (1m to 24h) |
| `--host-name` | stringArray | — | Name the delivered SSH host certificate must carry (repeatable; default: the system hostname) |
| `--json` | bool | — | Emit the result as machine-readable JSON |
| `--kit` | string | — | Kit slug to record (default: the kit of the workspace StackSpec) |
| `--local-node` | string | — | Exact local Node in the supplied ResolvedPlan |
| `--management-source` | stringArray | — | Network that must always reach ssh, as a CIDR (repeatable) |
| `--mode` | string | `standard` | Lifecycle mode to record: standard, or advanced when Techstack manages this deployment |
| `--no-record` | bool | — | Do not write the post-repair evidence under .stackkit/ |
| `--resolved-plan` | string | — | Verified canonical ResolvedPlan whose declared listeners to judge exposure against |
| `--site-kind` | string | — | Site kind of this host: home or cloud (default: inferred from the kit; modern-homelab needs it) |

**Examples**

```bash
# See what would be repaired
sudo stackkit host security repair --site-kind home

# Restore only the firewall, keeping a jump host reachable
sudo stackkit host security repair --apply --control firewall.default_inbound --management-source 198.51.100.0/24
```

### stackkit host ssh apply

Apply a sealed SSH CA trust, revocation or host certificate delivery from stdin.

Read one sealed ssh-ca-trust, ssh-ca-revoke or ssh-host-certificate envelope on stdin, signed by the pinned delivering authority, and apply it to this server's sshd:

```text
  - ssh-ca-trust installs the owner's user CA keys as TrustedUserCAKeys
    (/etc/ssh/stackkit/trusted_user_ca_keys) and one AuthorizedPrincipalsFile
    per local user (/etc/ssh/stackkit/principals/<user>). Root is never a
    target. An empty key list revokes like ssh-ca-revoke.
  - ssh-ca-revoke removes that trust. Revocations take effect at once and are
    never rolled back; one sshd cannot reload for is recorded as cleanup
    pending and finished by 'host security repair'.
  - ssh-host-certificate installs a host certificate beside the host key it
    certifies, only if it names every --host-name (default: the system
    hostname) and is currently valid.
```

sshd is reloaded only after 'sshd -t' accepts the new configuration; a change that fails is rolled back. The applied state is recorded in owner custody, so 'host security verify' reports drift and 'host security repair' reinstalls it.

```bash
stackkit host ssh apply [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--host-name` | stringArray | — | Name a host certificate must carry as a principal (repeatable; default: the system hostname) |
| `--owner-approve` | bool | — | Authorize changing this server's SSH access |
| `--tenant-ref` | string | — | Tenant the sealed delivery must be addressed to |

**Examples**

```bash
sudo stackkit host ssh apply --tenant-ref "$TENANT" --owner-approve < envelope.json
```

## stackkit host updates

Plan and apply operating-system package updates on this node.

Plan and apply operating-system package updates on this Debian or Ubuntu node.

The container runtime (docker.io, docker-ce\*, containerd\*, runc) is held: it is listed in the plan but never installed by apply, because upgrading it restarts every workload. Apply never removes packages, never runs autoremove, and never reboots; use 'stackkit host reboot' for that.

```bash
stackkit host updates [flags]
```

Subcommands: [`stackkit host updates apply`](#stackkit-host-updates-apply), [`stackkit host updates plan`](#stackkit-host-updates-plan)

### stackkit host updates apply

Install exactly the reviewed update plan.

Install exactly the package set a reviewed 'stackkit host updates plan' reported.

The pending set is simulated again first; when its digest differs from `--plan-digest` nothing is installed (plan_stale). apt runs non-interactively in a transient systemd unit (kombify-host-update-\*), keeping existing configuration files, so a CLI or agent timeout stops only the wait and never dpkg. The result records every package's version before and after and whether the node now requires a reboot.

```bash
stackkit host updates apply [flags]
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--json` | bool | — | Emit the stackkit.host-maintenance/v1 result as machine-readable JSON |
| `--plan-digest` | string | — | **Required.** plan_digest of the reviewed plan (sha256:&lt;hex&gt;) |
| `--yes` | bool | — | Confirm that the planned packages may be installed |

**Examples**

```bash
# Apply the plan you reviewed
sudo stackkit host updates apply --plan-digest sha256:<digest> --yes
```

### stackkit host updates plan

Refresh the package index and show what 'stackkit host updates apply' would install.

The result lists every pending package with its current and new version, the held container-runtime packages, packages apt keeps back, whether a reboot is likely (kernel, C library or systemd), and dpkg problems. plan_digest binds the exact package set; apply refuses when it no longer matches.

