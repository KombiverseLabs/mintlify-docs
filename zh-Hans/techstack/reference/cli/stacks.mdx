## techstack api stacks create

在所有者的 Homelab 中创建 StackKit 部署。

根据以 `stack_spec` 提供的规范 StackKits stack-spec 负载，在经过认证的 B2C 所有者唯一的 Homelab 下创建一个内部 StackKit 部署。旧版 `/stacks` 路由和 `stack_id` 响应字段标识的就是该部署；它们不会创建或选择第二个 Homelab 产品。一个 TechStack 实例可以服务许多所有者，每个所有者都有自己的 Homelab。旧版 `user_config`/kombination 负载在此兼容边界上仍被接受。向导客户端应发送稳定的 `X-Idempotency-Key`；使用相同键和相同负载的重试会返回原始的部署、计划服务器和预配任务。

```bash
techstack api stacks create [flags]
```

<Warning>需要确认：此操作会创建 StackKit 部署并开始预配，可能会订购计费服务器。传入 `--yes` 或回答提示；未使用 `--yes` 的非交互式运行会在发出任何请求之前以退出码 9 停止。</Warning>

| | |
| --- | --- |
| HTTP | `POST /api/v1/stacks` |
| 更改状态 | 是 |
| MCP 工具 | `create_stack` |

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `--x-idempotency-key` | string | 稳定的向导尝试键。最多 256 个字符。 |
| `--mode` | string | 向导模式。可选值：`easy`、`techie`。 |
| `--name` | string | 栈名称。 |
| `--options` | object | — |
| `--provider` | string | 基础设施提供商（直接格式）。 |
| `--services` | string\[\] | 服务名称（直接格式）。 |
| `--stack-spec` | object | 由创建向导生成的规范 StackKits stack-spec.yaml 结构。存在时，它是预配的唯一事实来源，并为兼容起见存储为该栈的 user_config。 |
| `--user-config` | object | 旧版结构化配置，包括较早的 kombination 风格负载。新的向导客户端应发送 stack_spec。 |
| `--user-config-format` | string | 可选值：`json`、`yaml`。 |

## techstack api stacks managed-runtimes add

通过原生提供商控制添加一个托管节点。

为确切的自有 StackKit 部署创建或恢复一个确定性的 Add-Server 任务。标准的 `Idempotency-Key` 是必需的。使用相同的键重放相同的规范请求，会返回原始的任务、租约、运行时服务器、资源代际和提供商操作关联；以不同的意图重用该键会以 409 失败。

原始键从不持久化或返回。丢失的响应或不确定的原生准入结果只能使用相同的键恢复。HTTP 接受表示原生准入已持久化且提供商协调尚待进行；它从不声称虚拟机已经预配完成或处于健康状态。新的准入会以原子方式，将经过认证的租户/所有者容量槽位与租约代际和提供商操作一同预留。当权威的原生准入发现该有界容量已满时，会持久化一个不可重试的 403 结果，重放该被拒绝的任务会返回相同的结果。对已提交准入的精确重放会复用其现有预留。此版本没有自动释放预留的机制：仅有终态或本地停用状态并不会释放槽位。租约清单和功能交付标志从不授予或拒绝容量。托管环境中的新准入还需要以 v2 签名的商业运行时和提供商权益，以及已签名的 `cloud.runtime.credits` `managed_servers` 模式/限额决策；仅有功能标志从不授予提供商容量。自托管 OSS 改用其在构建时固定的静态版本清单策略，而不依赖 SaaS 权益。

<Warning>需要确认：此操作会为该 StackKit 部署订购一台额外的托管服务器，并会产生费用。传入 `--yes` 或回答提示；未使用 `--yes` 的非交互式运行会在发出任何请求之前以退出码 9 停止。</Warning>

## techstack api stacks resume-enrollment

在其确切的现有虚拟机上恢复一个逾期的托管节点等待。

对已持久化的、处于 `waiting_enrollment`、`waiting_provider_provision` 或 `waiting_canonical_guard` 状态且其 `next_resume_at` 已超过有界宽限期的任务，进行经过认证的幂等恢复。服务器会将自有 StackKit 部署、源任务、等待原因、确切租约、活动的 foundation 角色和规范节点作为一个操作进行校验。它会以原子方式结束该确切的源等待，创建或重新激活一个绑定到同一租约和节点的确定性替代部署，并在后续调用中重放该任务。在进入处理程序之前，队列 Worker 会以原子方式获取持久的 `tenant/stack` 兼容执行声明；这会在各 Techstack 副本之间串行化同一 StackKit 部署的不同任务。该声明会持久保持 `running`，直到处理程序退出，包括取消期间。此端点从不调用提供商的虚拟机创建，也不会选择更新的虚拟机。崩溃后被发现处于持久 `running` 状态的替代任务会保持失败关闭，作为同一任务报告，并且从不自动复制；运行时操作的协调仍是独立的运维事项。

```bash
techstack api stacks resume-enrollment <stack-id> [flags]
```
